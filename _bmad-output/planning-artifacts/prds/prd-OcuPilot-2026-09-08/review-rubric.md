# PRD Quality Review — OcuPilot

## Overall verdict
The PRD has a real thesis (an agent that proposes, the user confirms, the write runs as the user and is marked in the IRIS audit database, all on the vendor's own hidden API), states its decisions as decisions with the alternatives it rejected, and traces every requirement to a catalog row and a journey — for a chain-top document feeding UX, architecture and epics, that traceability is its strongest asset. The risk is concentrated in done-ness: the Glossary, FR-10, FR-12 and UJ-6 key a "conversation" two incompatible ways; ten Release 1 FRs (the polish week) carry no testable consequences; and FR-72's "default-disabled destructive writes" can switch off the Logs area's only agent write during the voting week that SM-3 is judged on. None of the three needs new research; each is a paragraph of decision, and fixing them before bmad-ux and bmad-architecture start is the difference between a clean extraction and a contradiction discovered in a story.

## Decision-readiness — strong
The PRD decides. Addendum §1 records twenty numbered decisions, most with the rejected alternative and why ("Rejected: per-user definitions (every new user hits the gate, keys multiply)"), and the PRD body carries the consequences rather than re-arguing them. Trade-offs name what was given up: §8 admits the admin API "overrides the idea document's preference for documented APIs because no documented route covers five of the six areas"; §12 states that silent login rests on a feature documented "do not use" and prices the fallback as "one extra login for portal-first users"; addendum §1 decision 20 softens the first-login gate against the brief and says so. The one `[NOTE FOR PM]` (§10.3) sits at a genuine tension — the owner's growth order versus the research's "largest engineering gap" — and carries it to Open Question 14 instead of resolving it by fiat.

The Open Questions are open: fifteen have a named trigger (kick-off, probe before FR-43, test before the listing) and one, 13, is honestly labeled closed. The cut line in §10.1 is the most decision-ready piece — five ordered steps with FR numbers on each — but it stops one sentence short of usable under pressure, and FR-9's promise that the agent stays a conduit for a cut editor holds for only one of the two reasons an editor gets cut.

### Findings
- **medium** The cut line has an order but no floor (§10.1, §3.2, SM-3) — Five steps are ordered, but nothing says which step is the "do not submit below this" line. §3.2 already concedes that screens alone are "a thin interface by the contest's own rule", and SM-3 needs step 3 complete in every area. On 2026-09-26 the builder needs the floor stated, not inferred from a metric. *Fix:* add one sentence to §10.1 naming the floor ("Release 1 is not submittable until steps 1–3 are complete in all six areas") and what happens if it is missed in one area.
- **medium** FR-9's "agent remains a conduit" holds for time-cuts, not payload-cuts (§5.1 FR-9, §10.1, §12 row 1) — FR-9 says an unfinished large editor's "write tool for that editor's action still ships"; §12 row 1 extends FR-9 to "any write that cannot be made to work". If the editor is cut for time, the write tool can ship (only the Angular form is dropped). If it is cut because the admin API payload cannot be made to work, the write tool fails identically, since FR-17 requires "the same endpoint and payload shape the corresponding screen uses". The PRD promises the conduit in both cases. *Fix:* split FR-9's second consequence into the two cases; for a payload-cut, state that the write tool is withdrawn from the tool set and the agent says so when asked.
- **low** §5.1's description asserts what FR-1 hedges (§5.1 description, FR-1, Open Question 15) — the description says "afterwards the classic portal and the vendor's editors are signed in too"; FR-1 says the classic portal "is expected to" be, pending Open Question 15. *Fix:* hedge the description identically or drop the classic-portal clause from it.

## Substance over theater — strong
Three named personas plus "the builder", and each one moves a decision: Dana drives silent-first sign-in, the first-login gate and the proposal card; Marcus drives read-only mode, the kill switch, the local-model provider and the egress line; Priya drives FR-67 through FR-69 and the judging-order rule in §5.12. No persona is decorative. The innovation claim in §2 ("Nobody ships an assistant inside the IRIS portal") is backed by a seven-row competitive table (addendum §9) that names the specific gap — execute-with-approval plus an agent marker in the audit trail — rather than asserting novelty in general. The NFRs are product-specific and numeric where it matters (two seconds, ten seconds, one thousand rows, WCAG 2.1 AA "for the default theme; formal certification is not claimed"); NFR-3 through NFR-7 read like security decisions, not boilerplate. The Vision could not be swapped into another PRD: it names the right-docked panel, the hidden `/api/admin` v2 service, the contest number and the two invariants that never move.

### Findings
- **low** SM-6 has no horizon (§11 SM-6) — "In rising order" gives three rungs of vendor attention but no date by which any must appear, so the metric can never be judged failed. *Fix:* attach a checkpoint ("by the Stage 2 release" or "within 90 days of the winners' announcement") or move it to §1 as an aspiration.

## Strategic coherence — strong
There is one bet and the document follows it: the agent is the main conduit for editing (§1), so every screen gets a read tool and every action a write tool (§5.3, FR-16, FR-17), the cut line protects the agent core ahead of every write form (§10.1 step 2 before steps 3–5), and a cut editor's write tool still ships so the bet survives the cut. The success metrics test the bet rather than activity: SM-3 (six areas, six confirmed writes), SM-4 (install to confirmed agent write with highlight and marker in under a minute) and SM-5 (zero agent-marked writes without a matching confirmation) are the thesis restated as measurements. The counter-metrics bite: SM-C1 counts a screen without its read tool "against SM-3, not toward it", and SM-C2 forbids trading the confirmation for demo speed. SM-2 is the one activity metric, and it is justified by contest mechanics (earlier submissions list higher) and bounded by SM-C3. The scope kind is a contest-win problem-solving MVP, and §10.1's order (reads, then the agent, then small writes, then editors) matches that kind rather than "easy first".

### Findings
None that add information.

## Done-ness clarity — adequate
FR-1 through FR-69 each carry one to six consequences, and the best of them are exactly what a story needs: the endpoint, the state and the failure path (FR-3's version mismatch versus 403 rendering, FR-14's two-second highlight and the toast when the screen is not open, FR-17's server-side confirmation binding, FR-18's "same 403 the screen would", FR-66's twice-run install, FR-67's clean-clone and durable-volume cases). Where a field list depends on an instance probe, the FR says so and names the source (FR-45, FR-52, FR-53, FR-59). That is the strong half.

The other half is where the rubric says to be unforgiving. The Glossary's "conversation" and FR-12 key it to a screen context while FR-10 and UJ-6 carry it across routes, so two Release 1 stories cannot both pass. The ten polish-week FRs — Release 1 by the Glossary's own definition — have no consequences at all, and two of them (FR-70, FR-71) are ordered first because voters see them. FR-72's governance default can undo FR-63's consequence during the voting week. Beneath those, a cluster of "bounded" and "small" without a number, an acceptance criterion delegated to a sibling repository (FR-24), and a redaction requirement with no rule (FR-21) leave the engineer choosing values the tester then cannot check.

### Findings
- **high** "Conversation" is keyed two incompatible ways (§4 Glossary, FR-10, FR-12, FR-72, UJ-6) — The Glossary defines a conversation as "the sequence of turns the panel holds for one screen context"; FR-12 says "The transcript for the current screen context is loaded when the panel opens"; FR-72 says "Chat history persists by screen". But FR-10 says "Route changes keep the panel and its conversation", and UJ-6 runs a single conversation from Home to the task details screen and ends with a proposal there. A story for FR-10 and a story for FR-12 cannot both pass as written, and FR-12's lock ("A turn already in progress on the same conversation") has an undefined scope. *Fix:* decide once in the Glossary — conversation is per browser tab and continuous across routes, with screen context re-sampled per turn as FR-11 already says, and transcripts stored per user per session; or conversation is per screen and navigation starts a new one — then correct FR-10 or FR-12/FR-72 to match and re-read UJ-6 against the choice.
- **high** FR-72's "default-disabled destructive writes" can remove the Logs area's only agent write during voting (FR-72, FR-63, §10.2, SM-3) — FR-63 states "Delete is a write tool with a proposal, so the Logs area has a confirmable agent write (SM-3)". FR-72 ships a governance policy in the polish week with "default-disabled destructive writes"; "destructive" is defined nowhere, and every Release 1 delete (users, roles, web applications, SSL/TLS configurations, tasks, application errors) plausibly qualifies. §10.2 rules that "Nothing in the polish week may break a Release 1 screen", but this breaks a Release 1 agent write while judges vote on the published build. *Fix:* define "destructive" in the Glossary or enumerate the affected `tool:action` keys, and state that the polish-week frozen baseline enables every P0 write key so SM-3 holds through 2026-10-04; default-disable only keys added after Release 1.
- **high** Ten Release 1 FRs carry no testable consequences (§5.12 FR-70 through FR-79) — Release 1 includes the polish week ("plus P1 rows during the voting week", §4). §5.12 says "the epics work carries the row-level fields", which covers field lists but not behavior. FR-70 and FR-71 are ordered first because voters see them; FR-72 carries security behavior — "Log and tool content is sanitized before it reaches the model", administrators "can open any user's transcripts" — with no statement of what sanitized means or what a test would check. *Fix:* give FR-70, FR-71 and FR-72 the same consequence block as the P0 FRs (three to five lines each); leave FR-73 through FR-79 as row lists with a one-line "done when" apiece.
- **medium** NFR-2's freeze bound is unfalsifiable (§6 NFR-2) — "No turn may appear frozen for longer than the interval between tool calls" is satisfied by a ninety-second single model step with no tool call, because the interval is whatever the model takes. NFR-1's ten seconds covers only first progress. *Fix:* state a maximum silent interval (a heartbeat or elapsed-time indicator refreshed at least every N seconds), or state that between tool calls the panel shows a live timer and nothing more is promised in Release 1.
- **medium** Bounds named "bounded" without a bound (FR-23, FR-27, FR-60, FR-62, §8) — "up to a bounded count" (FR-23 retries), "a small token budget" (FR-27), "a bounded tail of the file" (FR-60), "bounded pages" (FR-62), "a bounded iteration count" (§8). The addendum gives 90 s and 300 s for the timeouts but none of these five. An engineer will pick numbers; a tester cannot. *Fix:* put each number in the consequence, or write "configurable, default N" on each line.
- **medium** FR-24's acceptance criteria live in another repository (FR-24, addendum §5, §8) — "The eleven server-side validation rules harvested from iris-session-agent apply" is the FR's main consequence, and the rules are enumerated nowhere in the PRD or addendum (both repeat "the eleven validation rules" by count only). *Fix:* list the eleven rules in addendum §8 so the epic has its acceptance criteria without opening iris-session-agent.
- **medium** FR-21 redaction has no rule (FR-21, NFR-5, SM-5) — "Secrets, credentials and tokens are redacted from ledger rows": tool arguments are arbitrary JSON, so which fields and patterns count is the entire test, and NFR-5 and the SM-5 audit chain depend on it. *Fix:* name the rule — a field-name denylist (password, key, secret, token, credential and their variants) plus the per-provider key shapes from FR-26 — and add one consequence: "the ledger row for a create-user call (FR-36) never contains the password value".
- **low** FR-3's identity mismatch has no consequence (FR-3) — the FR promises to verify "the instance identity matches what it last saw", but the consequences cover only version mismatch and 403. What identity is compared (GUID, name) and what happens on mismatch are unstated. *Fix:* add one consequence naming the identity field and the behavior (clear tab storage and show a notice, or silently accept and update).
- **low** FR-7 and FR-73 disagree on persistence scope (FR-7, FR-73) — FR-7 has sort, filter, page size and maximum rows "persisted per screen" in Release 1; FR-73 lists "keep UI state across sessions" as polish week. *Fix:* qualify FR-7 as "persisted per screen for the browser session", so FR-73's row is the cross-session upgrade.

## Scope honesty — strong
The Non-Goals in §9 do work: nine exclusions, most naming the stage that picks them up ("Undo is Stage 5", "free-form SQL ... comes with its guard in Stage 3") and two that are permanent (single instance, no secrets displayed back). §3.2 names the non-users, §10.4 lists what Release 1 leaves out, and the cut line says what gets dropped in what order rather than letting the reader discover it. De-scoping is recorded with a date and an owner: token metering to Stage 2, the agent picker to Stage 3, the daily-improvement measure narrowed to the voting week (addendum §1 decisions 9, 15, 16). §8 and §12 are unusually candid about the foundation: "its write payloads were not [observed]. Every write requirement in 5.5 through 5.10 is built against an unverified contract."

Open-items density is acceptable for a green-light PRD because none of the items hides a decision. Fifteen open questions, one `[NOTE FOR PM]`, zero live `[ASSUMPTION]` tags. Six of the questions are contest administration (1, 2, 3, 8, 10, 12), five are instance probes with a named trigger (4, 6, 7, 15, 16), two are staged (11, 14), and one is legal with a date (9). The build-blocking set — 6, 7, 9, 15, 16 — each says when it must be answered and which FR waits on it.

### Findings
- **low** The Vision's absolutes outrun the cut line (§1, §10.1 step 5, FR-9) — "every list reads live, every editor writes live" and "not demo screens" versus cut-line step 5, where large editors ship as links to the classic page. *Fix:* "every editor that ships writes live; an unfinished editor links to the classic page (FR-9)".

## Downstream usability — adequate
The Glossary is the best part of the document for a chain-top PRD: forty-three terms, a "must use these terms exactly" rule, deliberate separations (audit database versus agent audit ledger, kill switch versus the unconfigured state, read tool versus write tool) and a naming rule ("Never shortened to 'co-pilot' alone") that the body honors in every instance. IDs are contiguous and unique — FR-1..79, UJ-1..6, SM-1..6 with SM-C1..C3, NFR-1..14, Open Questions 1..16 — every parenthetical FR and Open Question cross-reference resolves, every FR cites its catalog rows, and each UJ has a named protagonist with context inline. Sections stand alone.

The hazards are specific. The "conversation" conflict above is the largest and is counted there. Beyond it: Home is the landing screen in three journeys and has no requirement; three APIs that FRs depend on are absent from the Glossary while the nearest-sounding one ("admin API") is defined; FR-15 quietly requires a mechanism (a browser-executed tool inside a server-side turn) that architecture will otherwise meet for the first time in a story; and "the shell" is used eight times without a definition.

### Findings
- **medium** Home is a screen with no requirement (UJ-1, UJ-2, UJ-6, §5.1, FR-73) — Home is where UJ-1 and UJ-2 land and where UJ-6 starts, and UJ-6's entry state is "the Task Manager line in the panel's suggested view", which is FR-70's suggested prompts (polish week), alongside FR-73's "Home system information panel" (also polish week). No Release 1 FR says what Home shows, so UX cannot design the landing screen and UJ-6 as written cannot be demonstrated on 2026-09-27. *Fix:* add a Release 1 FR under §5.1 for Home (even "Home shows the six areas, the header strip and the panel; the system information panel is FR-73"), and restart UJ-6 from the Tasks list or from a typed question with no suggested view.
- **medium** Three APIs used by FRs are missing from the Glossary (§4, FR-33, FR-34, FR-60, §8) — "management API" (FR-33, FR-34, §8), "monitoring API" (FR-60, §8) and "Atelier API" (§8, §10.3) appear in requirements; only "admin API" and "OcuPilot API" are defined. "management API" and "admin API" are near-synonyms in plain English and an architecture writer will conflate them. *Fix:* add "management API (`/api/mgmnt`)", "monitoring API (`/api/monitor`)", "Atelier API (`/api/atelier`)" and "interop-editors API" to the Glossary with one line each.
- **medium** FR-15 implies a mid-turn server-to-browser tool channel nothing else provides for (FR-15, FR-18, FR-21, addendum §3) — Navigation tools "run client-side and are listed in the agent's tool set as read tools", yet the agent loop runs on the instance (FR-18's token requirement, FR-21's ledger, addendum §3's "run turn" endpoint and progress channel). Executing a tool in the browser while a server turn waits for its result needs a second channel beyond the one-way progress feed. The PRD is right not to design it, but it should name it so architecture does not meet it in a story. *Fix:* one sentence in FR-15 or addendum §3: "Client-side tools pause the server turn for a browser round trip; the mechanism is an architecture decision alongside the progress channel."
- **low** "the shell" is used eight times and never defined (§4, FR-1, FR-3, FR-8, NFR-10) — §5.1's title "Portal shell and sign-in" is the only anchor. *Fix:* add "shell — the Angular application frame that hosts every screen and the panel: sign-in, header strip, navigation, page chrome, error handling and auto-refresh".

## Shape fit — strong
The shape matches the product. A developer-facing portal with a novel interaction model needs journeys, and the six named-protagonist UJs are load-bearing rather than decorative — each maps to FRs by number and each FR names the journeys it realizes. Chain-top needs traceability, and catalog row IDs on every FR plus consequences per FR are exactly what bmad-create-epics-and-stories will consume. The brownfield-harvest character is handled correctly: addendum §5 separates reuse-as-is, adapt and do-not-inherit per sibling project, and FR-45 and FR-59 name the exported Zen classes as their field lists rather than pretending to specify them. Persona count (three plus the builder) is right for the audience. The document is not over-formalized for the six areas; its heaviest section, §10.3 with 358 rows and endpoint counts, is roadmap the owner chose to include (addendum §1 decision 4), and it is confined to one subsection and the addendum.

### Findings
- **low** Stages 2–6 and the polish week are roadmap in requirement clothing (§10.3, §5.12) — Nothing tells the epics work to stop at Release 1; §10.3 carries row counts and gating criteria detailed enough to read as scope, and §5.12's FR numbering gives P1 rows the same standing as P0. *Fix:* one sentence at the top of §10: "Epics and stories are created for Release 1 only; §10.3 is the public roadmap and is not decomposed until each stage is planned."
