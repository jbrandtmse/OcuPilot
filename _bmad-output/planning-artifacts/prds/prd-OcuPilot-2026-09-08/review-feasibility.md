# OcuPilot PRD: feasibility review

Scope: is the plan in `prd.md` §10.1 executable by one developer between 2026-09-08 and 2026-09-27, and is the polish week to 2026-10-04 real. This is a feasibility pass, not a redesign; every fix below is a change to the PRD text, the cut line or the open questions. Day numbering: D+0 is 2026-09-08, the listing date 2026-09-14 is D+6, the deadline 2026-09-27 is D+19.

Facts checked outside the three documents while reviewing (all read-only): the repository has no source yet (`src/` is empty, no Dockerfile, no Angular workspace, only `docker-compose.yml`); the four sibling repositories were sized on disk; the running `ocupilot-iris` instance was queried in `%SYS` for the hidden admin API classes; and the contest-rules digest was reread for the exact wording of the "fully functional" rule. The PRD and addendum were rewritten at 12:21 while this review was in progress (the rubric and agent-safety reviews' fixes, addendum decision 21); this review was re-checked against that text and the findings below refer to it.

## Verdict

The product design is sound and unusually well evidenced, but the plan as specified is not credible: 119 P0 rows plus a ported agent runtime plus a Docker/IPM install path is roughly 45 developer-days of work against 19 (about 40 before the 12:21 safety fixes), and even the cut line's steps 1 to 3 (every read, the agent core, every small write) come to about 34. The head-start claim in §2 ("the 19 days go to screens and the agent rather than to a runtime") does not survive a look at the sources: the reusable part of iris-session-agent is about 9,300 of its 50,800 lines, it has no REST layer, its loop is synchronous and its tools run in-process, and the Angular side is a from-scratch build with iris-couch's admin UI as the only pattern source. Three things make the plan executable without changing the product: (1) replace "all P0 rows by 2026-09-27" with an explicitly named floor build (install path, shell, one list and one confirmed agent write per area, the panel, the config screen) and a stretch list in cut-line order; (2) make the architecture decisions the PRD defers to "architecture" on D+1 and D+2, because the tool-execution transport alone decides the token problem, the progress channel, the value of the execute-mcp harvest and the cost of all 37 write tools; and (3) recost the write-payload risk, which is over-weighted: all 82 hidden `%Api.Admin` classes are undeployed and their source reads back in full from the instance, each endpoint declaring its fields in a `Schema()` method behind one `RunPut`/`RunPost`/`RunDelete` base pattern, so "unobserved write payloads" is a half-day export-and-read task on D+1, not a per-story probe. The agent-safety fixes applied at 12:21 (server-minted proposals with fingerprint re-check, a protected OcuPilot database with confined escalation and a proof test, a seeded-injection test, per-user turn limits, audited switch changes, the egress chip) are the right requirements and add three to four more days that the cut line does not yet acknowledge. With those three changes a submittable, non-embarrassing build on D+6 and a winning-shaped build on D+19 are reachable; without them the large editors and the polish week are fiction and the demo path in UJ-3 has at least four unowned failure points.

## Critical path, with resolve-by dates

1. **D+1 (09-09). Tool execution transport, progress channel and confirmation flow shape.** Decide whether tools run in-process under the caller's IRIS session (the session-agent and execute-mcp model) or over HTTP against the admin API with the user's Bearer. In-process removes the 60-second token problem, makes the execute-mcp handler bodies the tool bodies, and lets the turn run inside a held request with the panel polling a progress endpoint; over HTTP requires refresh-inside-the-turn and makes the execute-mcp harvest a Stage 5 item. Decide at the same time that a turn ends at the proposal and that Confirm executes in its own request (no loop suspension); FR-17's new lifecycle (server-minted proposal, fingerprint at proposal time, re-read at confirm) already implies that shape.
2. **D+1. Export the 82 `%Api.Admin` classes to a reference folder** (`%Compiler.UDL.TextServices.GetTextAsString` in `%SYS`; verified today: `Deployed=0` for all 82, `%Api.Admin.Endpoints.Security.User` is 6.6 KB with `Schema()`, `ObjToJson()`, `ValidateQueryParams()`, and the base `%Api.Admin.Endpoint` exposes `RunPut`, `RunPost`, `RunDelete`, `ValidateRequest`, `NeedsRequestBody`, `ShouldRunAsync`). Tabulate the field list and `ResourcesOR()` per write endpoint; this also answers the X.509 backing class (Open Question 4) and gives FR-4 its per-screen resource map.
3. **D+2 (09-10). Build-versus-start install on the durable volume**, proven by four runs from a clean clone: `up`, `down` then `up`, `up` with a newer image against the existing `iris-data`, and `up` on a machine without `iris-data`. The Angular bundle lives in the image so it upgrades for free; the ObjectScript classes live in the durable database so the start path must reload them. Design the protected OcuPilot database, its resource and the confined escalation (addendum §6, FR-29) into this same install path now; retrofitting it later touches every storage class. Nothing else can be tested honestly until this works.
4. **D+2. Token strategy**, settled by item 1 if in-process; otherwise mint the shell's pair from `/api/ocupilot/login` with a 300-second access timeout and add refresh-inside-the-turn to FR-18.
5. **D+3. Pull the legacy CSP pages out of the container** (`UtilSysTaskBuilder.csp`, `UtilSysTaskOption.csp`, `UtilDashboard.csp`, `UtilSysConsoleLog.csp`, `UtilSysAppError*.csp`, `UtilSecAction.csp`, `UtilSysMonitor.csp` under `/usr/irissys/csp/sys/`): one `tar`, one hour. Confirms the messages.log path and the `^ERRORS` layout for LG-03 and LG-04, which are P0 reads needed by about D+9; the task wizard fields are only needed if TM-12 survives the cut.
6. **D+4 (09-12). Submit the Open Exchange listing for moderation** (public repository, README, license, screenshot). Open Exchange publication has its own review and the contest application requires a published listing; submitting on D+6 risks not being listed until D+8 or later.
7. **D+5. Web Gateway response timeout set in the Docker image and proven with a turn longer than 60 seconds; auditing state on a fresh container verified.** UJ-3's audit-marker climax fails silently if auditing is off or the OcuPilot user events are created disabled.
8. **D+6 (09-14). Floor build published; kick-off webinar; technology-bonus post; re-plan FR-79.** Ask at the webinar which "management APIs" InterSystems expects; a hidden API is a plausible objection under the Applicability criterion.
9. **D+12 (09-20). Plain IRIS Community check** (`USER` namespace, environment-variable credential rung only), 30 minutes; pin the image tag and confirm the arm64 image exists.
10. **D+15 (09-23). Freeze the demo path**, record the video, finish the README. Anything landing after this that touches UJ-3 forces a re-record.
11. **Not on the path:** Open Question 15 (classic-portal direction of silent login); the form login already covers the judge's arrival.

## Findings

### Critical

- **[critical]** The arithmetic does not close (§10.1, §5, §2) — About 43 developer-days are specified for 19; the cut line's steps 1 to 3 alone are about 31. The shortfall is not in any one area: the shell and install path are five to six days before the first screen exists, the agent runtime and panel are seven to eight, and the eight large editors are eight on their own. *Fix:* Replace "all P0 rows by 2026-09-27" in §10.1 and the Release 1 definition in the glossary with a named floor build plus a stretch list in cut order, and say in §12's second risk row that at most two large editors will ship. Keep the 119-row inventory as the traceability target, not the commitment.

- **[critical]** Tool execution transport is unresolved and FR-17, FR-18 and FR-9 pull in different directions (addendum §2, FR-17, FR-18, FR-9) — FR-17 requires "the same endpoint and payload shape the corresponding screen uses"; FR-18 requires tools to run under the user's own token through a turn that outlasts the 60-second access token; the addendum offers three candidate transports; the harvested session-agent tools are in-process (zero `%Net.HttpRequest` under `Tool/`, sixty in-process `%SYS`/`Ens`/SQL calls) and so are execute-mcp's handler bodies. Whichever transport is chosen changes the cost of all 37 write tools, the progress design and whether the execute-mcp harvest is worth anything in Release 1. The 12:21 text makes the split visible: FR-18 now speaks of "tokens the instance holds on the user's behalf during a turn" and of escalation "not in effect while tool code, admin API calls or provider calls run", which presumes tools calling the admin API over HTTP with the user's token, while addendum §5 still harvests in-process tool bodies. Left to "architecture" it will be decided on D+4 after the runtime port has started. *Fix:* Decide on D+1 (critical path item 1). If in-process, amend FR-17's last consequence to "the same backing operation and field vocabulary the screen's endpoint uses" and note that the tool path and the screen path are two callers of one operation. If over HTTP, add "the runtime refreshes the token pair inside a turn" to FR-18 and move the execute-mcp handler harvest out of the Release 1 harvest map.

- **[critical]** The write-payload risk is mis-costed and its mitigation is the expensive one (§8, §12 row 1, Open Question 6, addendum §3, FR-43, FR-46, extract §6(i)) — The PRD treats every admin API write as "built against an unverified contract until the payload is exercised on the instance" and makes "exercise the payload" the first task of every write story. The hidden classes are not deployed; their full source reads back from the instance, and every endpoint follows one base pattern with an explicit field schema. Reading the schemas is a half-day; probing 40 payloads one story at a time is three to four days spread across the sprint, at the worst moments. *Fix:* Close Open Question 6 with "export and read the endpoint classes on D+1; probe one PUT, POST and DELETE per family for partial-versus-full body semantics"; rewrite §12 row 1's mitigation accordingly; drop the "instance probe as first task" clause from FR-43 and FR-46 in favor of the exported schema.

- **[critical]** Two "large" rows hide 75 tools (CP-12, CP-13 in §10.1; FR-16, FR-17, FR-14) — The count of 12 large rows treats the entire agent tool surface as two items. FR-16 asks for "exactly one read tool over the same endpoint, returning the same fields the screen shows" and FR-14 asks every list to consume change events for its entity type. Hand-written, that is 38 read tool classes, 37 write tool classes and a per-screen subscription, about ten days that appear nowhere in the budget. *Fix:* Add to FR-16 and FR-17 a consequence that read tools, write-tool input schemas and change-event entity types are generated from the same endpoint descriptor the screen is built from, so adding a screen adds its tools without new tool code; state in §10.1 that CP-12 and CP-13 are costed on that assumption.

- **[critical]** The 2026-09-14 build is not reachable with the cut line as ordered (§10.1, SM-2, PK-03) — Foundation and install alone are five to six days; step 1 as written ("every list and detail screen with its read tool", 38 rows including the audit search) is seven to eight more. Nothing submittable exists on D+6 under the stated order, and the Open Exchange listing needs moderation time before the application can be made. *Fix:* Define the D+6 build in §10.1 explicitly: clean-clone install path, form login, shell with six-area navigation, one live list per area, README with working install steps; the panel in read-only question-answering over those six lists if it fits, otherwise the config-empty state. Submit the listing for moderation on D+4.

### High

- **[high]** The cut line omits the shell and the install path and puts "every list" ahead of the agent (§10.1) — Steps 1 to 5 do not mention 5.1 or 5.11, which are prerequisites for every step; and step 2, the agent core, cannot be verified end to end without at least one write, which step 3 withholds. *Fix:* Reorder to: 0. shell and install path; 1. shell reads plus one list per area; 2. agent core plus one confirmed write per area (this is SM-3) plus the UJ-3 fixture; 3. remaining reads; 4. remaining small writes; 5. medium editors; 6. large editors. Each step then ends in a build that is worth publishing.

- **[high]** UJ-3's climax depends on auditing being enabled and on the largest read screen (UJ-3, FR-22, FR-61, FR-66, SS-14/LG-02) — Auditing is not guaranteed on a fresh Community container, user-defined audit events are created through `Security.Events.Create` and must be enabled, and "opens the audit database viewer and finds the event" requires the L-sized audit search (SS-14) with the marker filter. FR-22's new "agent writes are not being marked" banner means the failure is no longer silent, but on a fresh judge install that banner is the first thing seen after login, which is worse for UJ-5 than silence. *Fix:* Add to FR-66 that the installer enables auditing and the OcuPilot events, documented as a security-posture change; add to §10.1 that the floor build's audit viewer is a marker-filtered list of recent events, with the full search form in step 3.

- **[high]** No demo fixtures exist (UJ-3, UJ-5, UJ-6, FR-66) — UJ-3 needs `/csp/myapp` disabled, UJ-6 needs a task suspended after an error, the Logs area's confirmable write needs application errors to delete, and FR-66 says the installer "seeds no agent definition". A judge repeating UJ-3 on a fresh install has nothing to enable. *Fix:* Add a P0 row and an FR-66 consequence for a `demo` install option that creates the fixtures the README's walkthrough names, and make the README use it.

- **[high]** The README's happy path runs the demo on a local model (UJ-2, UJ-3, UJ-5, FR-25) — UJ-2 configures Ollama, UJ-3 then asks for a two-field tool call, and UJ-5 has the judge repeat both. Small local models are unreliable at multi-field tool calls; the differentiator will look broken on exactly the path the judge follows. *Fix:* State in FR-25 a minimum model capability for the write path and make the README's primary path a capable cloud or local model, with Ollama as the documented privacy option; add "the demo prompts of UJ-3 and UJ-6 pass against every shipped provider" to the D+15 freeze.

- **[high]** The Web Gateway timeout is "reported, not changed" in the one environment the judge uses (FR-23, PK-08, addendum §6) — The Docker image is OcuPilot's deliverable; a judge will not edit `CSP.ini`. A turn longer than the gateway's response timeout dies as a gateway error on the judge's machine. *Fix:* Split PK-08: the compose image sets the timeout; the IPM path reports it.

- **[high]** The agent-safety fixes added three to four days to Release 1 and the cut line did not move (FR-11, FR-17, FR-18, FR-19, FR-20, FR-22, FR-29, 7.3, NFR-6, addendum §6 and decision 21) — The 12:21 rewrite turned the proposal store into a lifecycle with fingerprinting, server-side diff, re-read before write, masked secrets and typed-name confirms; added a protected OcuPilot database with confined escalation and a test proving a `%DB_<ns>:RW` holder cannot touch it; added a seeded-injection test, per-user turn limits, audited switch changes and the egress chip. All of it is right, none of it is costed, and §10.1 still promises every P0 row. *Fix:* Split the additions into floor and stretch in §10.1: floor is the server-minted single-use proposal, secret exclusion, the state checks at confirm, the prohibited set and the protected database designed into the D+2 install path; stretch is the fingerprint re-read, the typed-name confirm, per-user limits and the seeded-injection test, which becomes the D+15 freeze gate.

- **[high]** Eight large editors are 40 percent of the budget and still counted as Release 1 (§10.1 step 5, §5.8, FR-30, FR-35, FR-38, FR-41, FR-42, FR-45, FR-52, FR-53) — Each is a day at best: 700 to 1,400 lines of Zen source per editor to re-express as reactive forms, with the two task pages coming from unexported CSP. *Fix:* Say in §10.1 which two ship if time allows (PM-07 user edit and WA-05 web application edit are the most used) and that the other six are FR-9 links in Release 1 with write tools built as get-merge-put over the exported schema.

- **[high]** The polish week is 61 rows in seven days with no test suite (§10.2, §5.12, PK-22, PK-23, SM-2) — Five of the rows are large (the four OAuth editors and SA-02), about twenty are medium, judges' feedback will need reaction time, and "nothing may break a Release 1 screen or a Release 1 agent write" is asserted with the test harness and CI both in P1, even though the 12:21 text now requires at least three Release 1 tests (FR-29 state protection, NFR-6 seeded injection, FR-3 route check) that have no harness to run in. *Fix:* Name the dozen rows that will ship (CP-23, CP-24, CP-25, CP-27, CP-30, CP-31, the article, the video and short, SS-17, SS-19, OS-14, SH-12), reserve three of the seven days for feedback, move SS-24..SS-27 and SA-01/02 to Stage 2, move PK-22 (the HTTP test harness) to P0 because the Release 1 tests need it, and pull a one-minute-demo smoke script (the UJ-3 path against a fresh container) into P0 as the gate before every publish.

- **[high]** "Reuse as-is" is overstated (§2, addendum §5) — On disk, iris-session-agent's reusable runtime is about 9,300 lines (Agent, LLM, Tool base and registry, Chat, Audit, Config, Util, Security, Task); 25,900 lines are tests bound to the `SessionAgent.*` names that PK-07 forbids, 4,400 are Zen UI to discard, 7,700 are interoperability tools for Stage 4. There is no REST layer, no progress hook, no proposal store; the `MutatesState` gate is the inverse of the write model; the four provider adapters must be re-verified against live endpoints. iris-execute-mcp-v2's bodies are ObjectScript behind the `%Atelier.REST` envelope the PRD excludes, so extraction is method by method. iris-couch's Angular 18 UI and its router, installer and static handler are the genuine head start. *Fix:* Rewrite §2's fourth bullet to "the agent core and the REST patterns are harvested; the runtime port is four to five days" and add the rename, the REST surface and the proposal store to the "new for OcuPilot" list in addendum §5.

- **[high]** A moving image tag under a hidden API (FR-3, NFR-8, PK-09, `docker-compose.yml`) — The compose file pulls `latest-cd`; a judge who pulls during the voting week can get a build where `/api/admin` v2 differs, and FR-3's blocking notice would then be the first thing they see. *Fix:* Add to FR-67 that the compose file pins the exact tag the release was tested on, and re-pin as part of each publish.

### Medium

- **[medium]** "Thin interface" misreads the contest rule (§3.2, §10.1, SM-C3) — The rule reads "fully functional … not an import or a direct interface for an already existing library in another language"; it is about wrapping libraries, not about screens without an agent. A GUI over the management APIs is the literal task. The misreading does not hurt the product, but it makes the D+6 floor look ineligible when it is not, and it is the stated reason for putting the agent ahead of writes. *Fix:* Reword §3.2's first bullet and make §10.1's agent-first ordering a differentiation argument, not an eligibility one.

- **[medium]** Four provider families in P0 (FR-25, CP-04) — The code is harvested; the cost is proving each adapter's tool-calling path against a live endpoint and debugging the drift, half a day each on the critical path. OpenAI-compatible alone covers OpenAI, Ollama, vLLM, LM Studio and most gateways. *Fix:* Contest build ships OpenAI-compatible plus one native adapter; the other two are re-verified in the polish week.

- **[medium]** Agent-driven navigation is cross-cutting and only UJ-6 needs it (FR-15, CP-43, UJ-6) — Every list must accept filter and selection from route parameters. *Fix:* Move CP-43 to the polish week; UJ-6's resolution becomes "the agent names the screen and the task" until then.

- **[medium]** The auto-refresh framework is P0 by dependency, not by value (FR-7, SH-09) — A refresh button satisfies the contest; the framework with "pause while a proposal is open" is polish. *Fix:* P0 is a manual refresh; SH-09 moves to P1.

- **[medium]** Per-user kill switch and per-user read-only toggle triple the switch UI (FR-19, FR-20) — The server-side flags are cheap; three surfaces are not. *Fix:* P0 is the instance-wide kill switch and enforced read-only on one administrator screen; the per-user variants are polish week.

- **[medium]** The OpenAPI path-and-verb browser and the selective SQL auditing wizard are hidden inside P0 rows (FR-34, FR-47) — Both are medium-to-large pieces of UI with little judging value. *Fix:* FR-34's Release 1 view is the raw document with search; the selective SQL auditing wizard is struck from FR-47.

- **[medium]** "Generated OpenAPI document under automated test" with no CI in P0 (FR-3, NFR-8, PK-23) — There is nowhere for the test to run. *Fix:* Reword to "a startup check that each route OcuPilot uses answers, surfaced through FR-3's notice" plus one `%UnitTest` method.

- **[medium]** "A cut editor's write tool still ships" is true only under conditions the PRD does not state (FR-9, §10.1, addendum §1 item 17) — A write tool for a 25-field editor needs the same field knowledge and payload mapping as the form; it saves the form UI, not the contract. It is cheaper than the form when its schema is generated from the exported endpoint schema and it does get-merge-put; it is a demo landmine when it has never run. *Fix:* Add to FR-9: "a write tool ships only after one successful end-to-end run on the instance; otherwise the agent offers the classic-page link."

- **[medium]** The durable-volume upgrade path is required but unproven (FR-67, addendum §6, Open Question 5) — "A newer image upgrades the installed OcuPilot without manual steps" means a start-time reload of the classes into the durable database on every start or on a version mismatch, and neither the vendor templates nor the research show it working. *Fix:* Close Open Question 5 on D+2 with the four-run test in critical path item 3, and record the chosen mechanism in FR-67.

- **[medium]** Cheap rows the contest would reward are in P1 (CP-23, CP-24, CP-30, FR-70, FR-72) — Suggested prompts per screen are a static map; explain-this-screen is a prompt over context already sent; the copy-out draft is a prompt instruction. A judge who does not know what to ask sees nothing. The 12:21 text already promoted the egress chip (CP-31) into Release 1, which is the right call. *Fix:* Pull these three into the floor build's step 2 alongside it.

- **[medium]** The judge may have neither a key nor a local model (UJ-5, FR-28, PK-16) — The screens work in the gate state, but the differentiator is invisible without a provider, and the online demo that would cover this is an optional bonus decided after the deadline. *Fix:* README states both paths and what works without a provider; decide the online demo (Open Question 8) by D+15, and if it runs, it runs in enforced read-only on a throwaway container with a spend-capped key.

- **[medium]** Ollama from inside the container is a README trap (UJ-2) — `localhost` inside the IRIS container is not the host; the endpoint must be `host.docker.internal`, and an environment-variable key set in `docker-compose.yml` needs a container restart to change. *Fix:* Add both to the README requirement in FR-69.

- **[medium]** Plain IRIS Community and Apple Silicon are unverified until the listing (FR-68, Open Question 16, NFR-13) — Both research containers were IRIS for Health on one architecture. *Fix:* One 30-minute check each at D+12; the README states exactly what was tested rather than claiming both editions.

### Low

- **[low]** The window is 20 calendar days, not 19 (§0, §2, §10.1) — 2026-09-08 through 2026-09-27 inclusive is 20 days. Harmless; use one figure consistently.

- **[low]** Keyboard operation of every screen is a verification cost, not a build cost (NFR-12) — Fine as intent; do not gate a publish on it in Release 1.

- **[low]** Coexistence with iris-execute-mcp-v2 does not need a test (FR-66) — Name isolation is enough; drop the automated-test clause.
