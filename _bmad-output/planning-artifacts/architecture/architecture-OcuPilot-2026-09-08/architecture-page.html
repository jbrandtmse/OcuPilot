An agent that changes your instance, and proves what it changed.

OcuPilot rebuilds six areas of the IRIS System Management Portal in Angular, with an agent docked beside every screen. The agent holds no privilege you don't. Every write it makes is reviewed, confirmed, and marked in the audit database as having come through it.

The problem, stated plainly

Six portal areas, about forty Zen-era pages, terse errors, and no help beyond a documentation link.

InterSystems has deprecated the classic portal but only partly replaced it — the vendor's new Angular interface covers interoperability, not administration. Meanwhile the instance already carries a capable, undocumented admin API that five of the six contest areas sit on.

So the interesting question was never "can these screens be rebuilt". It was whether an assistant can be given real write access to security configuration and still be something you'd run on a production instance. That answer is a set of invariants, and they are what this architecture is.

The write path

The one sequence the whole product rests on. Numbered because it genuinely is ordered — each step depends on the one above it, and three of them can refuse.

01

The agent asks for a writeagent

It calls a write tool. The tool does not write. It reads the target fresh, in the calling process, with the signed-in user's own privileges.

02

The instance mints a proposal

Server-side: the resolved arguments, a fingerprint of the target's current state, the computed diff, and a single-use token. Secret fields are excluded from what is stored.

03

You review a diff the instance computed

Not one the model described. Before and after, the agent's rationale and expected impact as its own labelled text, and a ten-minute countdown.

04

You confirm — and only you canyou

Confirm is a request from your browser. It is not a tool, it is not in the tool registry, and it refuses any caller acting on the model's behalf. One confirmation per write, never batched.

05

The instance re-checks everything before it writes

Fingerprint still matching, your privileges still held, read-only and the kill switch still off, the target not on the prohibited list. Any one of those refuses the write.

06

The write and its marker commit together

The token is claimed and the write applied in one atomic transition, so two confirmations cannot both land. An audit event records the proposal, the target and you.

07

The screen catches up

The affected row re-fetches in place and highlights within two seconds. Ask "show me the audit entry" and the agent takes you to it.

Three decisions that made it feasible

Each was settled by probing the running instance rather than by reasoning about it. The proofs below are what the probes returned.

Where do tools run?
In process, as you

The admin API's endpoints are ordinary objects with a Run() method. OcuPilot calls them directly instead of over HTTP, so a tool inherits your identity from the process and needs no token at all.

What holds, whatever the model does

The model is assumed to be fully compromised by anything it reads — a log line, a user name, a task description. These are the properties that survive that assumption.

  • No privilege of its own
    No service account, no elevation on the request path. Every gate is checked in the calling process at the moment of the call. A refusal is reported, never retried.
  • Nothing unconfirmed
    No write occurs without a confirmation on a diff the instance computed. The confirm channel accepts only the fields declared secret — any other key is rejected, so what runs cannot differ from what you approved.
  • Some things are absent, not gated
    Deleting the last %All holder, disabling the service that serves OcuPilot, granting a role to anyone: not refused at a confirmation prompt — never offered as a tool at all.
  • Nothing unmarked
    Every confirmed write is registered in the IRIS audit database alongside the vendor's own record of the same change, carrying the proposal id so either one finds the other.
  • Nothing leaves quietly
    One outbound destination: the provider you configured. Screen context is capped, secret fields never travel, and the panel tells you when data leaves the instance.
  • Instructions come from you
    Untrusted text enters only as delimited tool results, never the system prompt. A seeded-injection test plants "ignore previous instructions" in a log line, a user name and a task description, and asserts zero proposals and zero outbound requests.

The turn runs in a background job that inherits your identity, so the browser is never held open for the length of a conversation and no gateway timeout has to be raised. That job reads and proposes; it never writes. The write happens in your confirm request.

What it does not do

It does not manage a second instance. It does not act without confirmation, batch approvals, or undo. It does not store an API key, a private key or a secret in any form it can show you again. It does not copy the vendor's bundles. It does not ship embedded Python. In this release it does not stream, does not localize, and does not target a phone.

Two lines do not move at any stage: the agent never holds a privilege the user does not, and every agent write stays visibly marked in the audit database.
