# technical research: OcuPilot portal feature landscape (contest rules, SMP parity inventory, API and embedding reality, harvest sources)

**Decision this research serves:** Which features OcuPilot ships by the contest deadline (contest minimum plus an always-on co-pilot agent), and the priority order of every later feature toward full System Management Portal (SMP) parity plus sibling-project functionality; feeds the product brief and PRD

## Executive summary

**Do this.** Enter the contest with a thin Angular UI over the REST services already on the instance, with the always-on co-pilot as the differentiator, and build nothing else before 2026-09-27. List on Open Exchange and apply on 2026-09-14 with a submittable build, then improve visibly through the voting week ending 2026-10-04. After the contest, grow toward full portal parity in the order the companion catalog gives: API-backed screens first, custom-REST screens second, the long tail as demand shows.

**Three findings drive that answer.**

1. **The contest floor is already API-backed.** The task names six areas verbatim [2]; five of them have REST routes on the instance today, chiefly a hidden, undocumented `/api/admin` v2 service verified live and present in the stock image [21], and only messages.log and the application error log need custom endpoints [20]. The 19-day plan is screens and an agent, not a backend (cross-dimension insight 2).

2. **The co-pilot's core and its safety layer exist in two different sibling projects.** iris-session-agent supplies providers, tools, audit and history; iris-execute-mcp-v2 supplies the permission model; neither has progress, propose-review-confirm writes or execution as the user, which is where the field converges [10][27][39][41] (insights 5 and 6). No prior entry and no vendor screen covers the six areas, and the field is empty [34][35][37].

3. **Everything after the contest sorts itself by API readiness.** The catalog holds 538 rows (535 distinct): 119 at P0, 62 at P1, 137 API-backed parity rows at P2, 164 custom-REST rows at P3 whose backing ObjectScript the MCP suite's handlers already wrap one for one [20][27], and 56 long-tail rows kept with the reason for exclusion.

**The biggest caveat is authentication.** Each REST application keeps its own session cookie, the vendor's Angular editors log in silently only through a Group by ID shared with the classic portal, a setting the documentation says not to use, and a minted JWT, and the cookie that carried the observed silent login was not isolated [20][22][25]; the first spike must settle it (insight 1). The second caveat is that `/api/admin` is unsupported; D4 and Recommendation 2 say how to pin and guard it [21].

**Evidence standing.** 45 sources; 26 ledger claims, of which 9 were verified by fresh-context checks, 1 is disputed (the MCP suite's exact tool count) and 16 rest on a single credible source; a semantic citation sample of 12 found no unsupported claim but three numeric corrections, now applied. The red-team pass was off.


## D1. Contest rules and judging

**Bottom line.** The contest is a 19-day sprint to a *submittable* build: submissions close 2026-09-27 23:59 EST, and improvements are explicitly allowed through the voting week ending 2026-10-04 [1][2]. The task statement is specific: a GUI "powered by InterSystems IRIS management APIs" covering six named Management Portal areas, with further screens optional [2]. Nothing in the rules constrains framework, API choice, or reuse of InterSystems UI assets beyond the originality requirement [1][2][3][7]. The full digest is `digests/contest-rules-r1-1.md`.

**The task, verbatim** [2]:

> Create a GUI powered by InterSystems IRIS management APIs for the following Management Portal tasks:
> - Manage web apps and explore REST APIs
> - Permission management
> - Security and Secrets management (with wallet, x509 creds, OAuth setup, etc.)
> - Task management
> - Operating system management (processes, disks, CPU, memory, devices, etc.)
> - All the logs - what's being reported to the user from various sub-systems
> - Feel free to add any other screens or actions you frequently use!

The Open Exchange (OE) page carries the shorter form "for certain Management Portal tasks" [1]. Whether an entry covering only some of the six areas is accepted is not stated; approval is at the experts' discretion "based on the criteria of complexity and usefulness", final and not subject to appeal [2].

**Timeline** (verified: two InterSystems sources for every dated row except the webinar; both pages write the timezone as "EST") [1][2][4]:

| Event | Date | Days from 2026-09-08 |
| --- | --- | --- |
| Contest opens, registration starts | 2026-09-14 00:00 EST | 6 |
| Kick-off webinar (Gervais, Singh, Logue) | 2026-09-14 12:00 EDT | 6 |
| Submission deadline | 2026-09-27 23:59 EST | 19 |
| Voting period | 2026-09-28 to 2026-10-04 23:59 EST | 20 to 26 |
| Winners announced | not stated anywhere read | |

**Hard requirements** (both [1] and [2]): fully functional; not an import, thin interface, or copy-paste of an existing library or app; new to Open Exchange or significantly improved; runs on IRIS Community or IRIS for Health Community (the OE page also lists IRIS Cloud SQL, a minor contradiction; the newer announcement governs); open source on GitHub or GitLab; English README with installation steps and either a video demo or a description; at most three submissions per developer or team. The OE page alone adds "a link to the idea" to the README requirement, single-source and cheap to satisfy [1]. The application must already be a published Open Exchange listing before applying (applications go through the contest page, the app's Contest tab, or the developer portal) [6][3] (medium confidence: the verifier found this only indirectly supported on the contest pages themselves). Deliberately obfuscated source is not allowed [3]. Teams of 2 to 5 must link every member's Developer Community (DC) profile in the README [2].

**Judging and prizes.** The OE page lists the criteria Complexity, Clarity of Instructions, Developer Experience, Applicability, and Usability (single-source; reads like the standard contest template) [1]. Experts nomination pays $5,000, $2,500, $1,000, $500, $300, then $100 for places 6 to 10; Community nomination $600, $400, $100; a new Freshmen nomination $600, $400, $100 for entrants with at most five prior contests and no prior top-three finish (amounts single-source) [2]. Community voting, by precedent from the immediately preceding contest, uses trusted DC members, one changeable vote each, blind counts with a daily leaderboard, and earlier submissions listed higher on the contest page (medium confidence) [8].

**Technology bonuses.** No bonuses post exists for this contest as of 2026-09-08, and the contest page itself says "Look forward to the announcement of the technology bonuses", so one is coming (verified; low confidence on what it will contain) [1][2][8]. The most recent precedent, the Full Stack Contest 2026 [5], awarded Vector Search 3, Embedded Python 3, DC Idea 2, Docker 2, IPM 2, Online Demo 2, Find a Bug 2, First DC Article 2, Second Article 1, YouTube Video 3, YouTube Short 1, and First-Time Contribution 3, for a stated maximum of 26; no Angular, AI, REST, or code-quality bonus appeared. A bonuses post is likely around the 2026-09-14 kick-off.

**What the rules do not say** (absence across six InterSystems pages, medium confidence): no framework restriction, no mandate to use REST, no prohibition on reusing InterSystems portal code or UI bundles, no named license, no definition of "management APIs", no winners date. Contest-specific Rules override the generic Terms, and InterSystems may move dates by notice on the contest page [3]. The Terms include an intellectual-property grant to InterSystems; read it before choosing a license [3][7].

**Implications for the brief and PRD** (inference from the cited rules):

- The six named areas are the contest floor; the co-pilot is the differentiator the rules invite under "any other screens or actions". Feeds the brief's scope and the PRD's must-have tier.
- Timing, the bonus items and the post-kick-off re-check are Recommendation 6 and the first row of Open questions.

## D2. Contest field, prior winners, InterSystems' own direction

**Bottom line.** The field is empty: the contest page's embedded data lists no participants, the announcement has one comment (a Freshmen-eligibility question), and the Management Portal tag carries no entrant posts; registration opens 2026-09-14 [34]. Prior art on Open Exchange is thin and dormant, nothing covers the six contest areas coherently, and InterSystems' own Angular-era interface has modernized interoperability surfaces only, none of the administration areas the contest names [35][37]. An agentic portal that covers all six areas has no credible incumbent. The tables of prior art and winners are in `digests/contest-field-r1-1.md`.

**Prior art that matters** [35]: bg-iris-agent (Banksia Global), an ObjectScript "AI IRIS Agent" that reads portal data and modifies non-critical settings, 2 stars, last push 2025-06, the nearest conceptual competitor; irislab (caretdev), explicitly pitched as a Management Portal replacement on TypeScript and Flask, 0 stars, dormant since 2024-08; apptools-admin (globals, SQL, export; a 2023 Developer Tools entrant); iris-history-monitor; iris-user-manager; IrisWebClient (a Pascal GUI that took a $100 tier in the Full Stack Contest 2026); WebTerminal. One unread lead: an Angular rebuild of the Production Monitor announced around March 2026, a plausible entrant. Rules allow dormant apps to re-enter "with a significant improvement".

**What winning looks like** [36]: fields are small (17 apps in Developer Tools 2025, 16 in Full Stack 2026), and a $100 tier for places 6 to 10 means roughly the top 60 percent of a field receives something. Winners posts publish placements only, never votes, scores or rationale. A stable cohort recurs across contests, and Community voting favored that cohort in 2026 while diverging from the Experts winner. The Experts top three in Developer Tools 2025 were editor and workflow tooling rather than standalone web UIs. Whether Docker, IPM or a demo video correlates with placement was not established. One relevant fact for eligibility: iris-table-editor took a $100 tier in Full Stack 2026, which does not count as a top-three finish, so the Freshmen nomination may still be open depending on the number of prior contests entered [36].

**InterSystems' direction** [37][38]: the 2026.1 release notes describe the new user interface as an opt-in experience and list only interoperability enhancements (Production Configuration, Message Viewer and Search, the BPL Editor embedded in VS Code, Rule Editor); 2026.2 adds a read-only Schema Viewer and states that all other interoperability screens remain in the standard interface (medium confidence, search extracts of the release-notes page). No evidence was found that security, users and roles, OAuth and X.509, tasks, OS views or logs have moved. Zen is deprecated, and a community question asks how to add custom portal pages "the new way", described second-hand as REST pages with JWT authentication bootstrapped from the session cookie (low confidence). Read together with D4's hidden admin API and its `/iris/api/admin/` location-header prefix, the inference is that InterSystems is building the administration API before the administration UI, and the contest targets exactly that gap.

**Implications for positioning** (inference): the differentiation case is Recommendation 9 and cross-dimension insight 10; the one point not carried there is that the kick-off panel includes the Analytics and AI product manager, the only organizer-side signal that AI is in scope [37].

**Feeds:** brief (alternatives and positioning), PRD (differentiation), go-to-market for the voting week.

## D3. SMP inventory

The four sub-sections inventory the classic portal by section: System Administration (90 menu leaves), System Operation (36), the portal shell with System Explorer (11) and Analytics (18), and Interoperability (68 live, 76 in source). Three of the contest's six areas live in System Administration and three in System Operation; the page mapping is the table in D4. Every leaf and action is itemized in `feature-catalog.md`, and each sub-section names its page-by-page digest.

### D3a. SMP inventory: System Administration

**Bottom line.** System Administration is the largest section of the portal: 90 menu leaves (Configuration 54, Security 30, Licensing 2, Encryption 4), generated in code by three methods of the portal application class with no data-driven menu table, and served by about 209 of the 296 exported portal classes (121 under `/csp/sys/mgr/`, 67 under `/csp/sys/sec/`, 21 templates and dialogs) [18]. Twenty-six pages are large by size or wizard structure; the biggest are the web-application editor, the mirror failover editor, the NLS locale editor, the three OAuth 2.0 editors, the database wizard and the user editor [18]. Eleven leaves point at seven legacy CSP pages absent from the export, so SQL Gateway, all five Database Backup entries, Web Gateway Management, Task Manager Email, Enable and Disable Auditing, and Security Advisor are a blind spot in this inventory [18]. The page-by-page table is in `digests/smp-sysadmin-r1-1.md`.

**Menu, condensed** [18]:

- **Configuration.** System Configuration (Memory and Startup, Namespaces, Local Databases, Remote Databases, Sharding with three items, Archive Targets, Journal Settings, WQM Categories, Log Daemon); Connectivity (ECP, SQL Gateway Connections, External Language Servers, Cluster); Mirror Settings (enable service, create, edit failover, edit async, join failover, join async); Database Backup (list, full, all on list, incremental, cumulative); Web Gateway Management; SQL and Object Settings (SQL, Objects, TSQL and ISQL compatibility, system and user DDL mappings); Device Settings (devices, magnetic tapes, subtypes, IO, Telnet); Machine Learning Configurations; National Language Settings (configured defaults, locale definitions, import); InterSystems Reports; Zen Reports (render, print, Excel servers, settings); Additional Settings (Compatibility, Advanced Memory, Monitor, Source Control, Startup, Task Manager Email, deprecated Shadow Server Settings).
- **Security.** Users, Roles, Resources, Services; Applications (Web, Doc DB, Privileged Routine, Client on Windows); Superservers; SSL/TLS Configurations; X.509 Credentials; OAuth 2.0 (Client, Resource Server, Server, Administration); Managed File Transfer Connections; System Security (system-wide parameters, authentication and web-session options, LDAP/Kerberos); Auditing (enable, disable, view audit database, configure system events, configure user events, copy, export, purge); Security Advisor; Mobile Phone providers.
- **Licensing.** License Key, License Servers. **Encryption.** Create key file, manage key file, database encryption, data-element encryption.

**Mechanics a replacement must reproduce** [18]:

- **Gates.** Configuration and Licensing need `%Admin_Manage:USE` plus READ and WRITE on `%DB_IRISSYS`; Security needs `%DB_IRISSYS:READ`; Encryption needs `%Admin_Secure:USE`; Journal Settings needs `%Admin_Journal`; Compatibility, Web Gateway Management and Security Advisor additionally need `%Admin_Secure`. OAuth 2.0 pages use their own `%Admin_OAuth2_*` resources, and many pages declare no resource at all, inheriting protection from their template or the web application.
- **Edition and feature gating is runtime**: Sharding is disabled unless the license allows it (it does not on this Community instance); the five Mirror leaves depend on the mirror-service state; Client Applications appear only on Windows; SQL Gateway and External Language Servers are hidden on VMS. Enterprise Manager read-only hooks are hard-coded off.
- **Backing API surface** the pages call: the `Config.*` package (namespaces, databases, mirrors, ECP, journal, archives, work queues, gateways, devices, NLS, license servers, startup, SQL, mappings), the `Security.*` package (users, roles, resources, services, applications, DocDBs, servers, SSL configs, LDAP configs, events, system), `SYS.Database`, `SYS.Mirror*`, `%SYS.Audit`, `%SYS.X509Credentials`, `%SYS.PhoneProviders`, `%SYS.ML.Configuration`, `%SYSTEM.License`, the `OAuth2.*` package and several routine entry points for encryption, mirroring and licensing.

**Instance versus export** [19]: the instance holds 308 portal classes; the 12 missing from the export are all Hidden (Shadows, FileMan and Zen Report twins). Five classes referenced from page code do not exist on the instance at all (a move-globals wizard, three sharding dialogs, an async-mirror-authorization dialog), so they are dead references, not parity targets. The live home page also shows a "Health" top-level entry injected by HealthShare, outside the exported application class.

**Contest areas in this section**: three of the six (web apps, permissions, security and secrets); the page mapping is the table in D4 [2].

**Leads** [18]: the Objects settings page resolves its backing class dynamically, and Shadow Server Settings is deprecated and excluded from parity; the remaining open items are rows in Open questions.

**Feeds:** PRD feature catalog (System Administration tier and the three contest areas that live here), architecture (Config and Security packages as the backend surface, runtime gating), and the D4 coverage map.

### D3b. SMP inventory: System Operation

**Bottom line.** The System Operation menu is generated by one method in the portal application class and holds 19 top-level entries (5 of them groups) and 36 leaf links (19 Zen pages and 17 legacy CSP pages); behind them sit 44 Zen classes and roughly 27 legacy screens, about 70 screens in all [11]. The whole section is invisible without `%Admin_Operate:USE`, and most items are additionally disabled without READ and WRITE on `%DB_IRISSYS`; Task Manager items and Diagnostic Reports need `%Admin_Task:USE` instead [11]. Nearly half the section is still pre-Zen `%CSP.Util.AutoPage` CSP: all Backup pages, all Journal pages, the System Dashboard, Shadow Servers, the New Task wizard, the Application Error Log, Messages Log, System Usage and Diagnostic Reports; their `.csp` source is not in the export, so those rows rest on pane classes and live renders [11][12]. The full page-by-page table with actions, backing classes and complexity is in the digest file `digests/smp-sysop-r1-1.md`.

**Menu, condensed** [11]: System Dashboard; Backup (full all, full list, incremental list, cumulative list, status, history); Databases with a Details page (mount, dismount, truncate, compact, defragment, a three-step integrity-check wizard); Processes with Details (variables, terminate, suspend, resume, broadcast); SQL Activity; Locks (view, manage/remove); Journals (list, view records, integrity check, profile, summary, switch journal, switch directory, mirror journals); Transactions; Shadow Servers (three pages); Mirror Monitor (about 15 actions, 3 dialogs); Task Manager (new-task frameset wizard with about 60 fields, on-demand, upcoming, schedule with details, per-task history, run, suspend, resume, delete, export, edit, import); LDAP or LDAP/Kerberos read-only configurations; System Logs (Application Error Log in three levels, Messages Log, xDBC Error Log, System Monitor Log, SQL Diagnostics Log); System Usage; License Usage; Interoperability Usage; Web Sessions (list, end); Background Tasks (list, info, errors, cancel, pause, resume); Diagnostic Reports.

**Mechanics a replacement must reproduce** [11]:

- **Long-running work** goes through `%CSP.UI.System.BackgroundTask.RunTask`, which validates the task name against a 44-entry whitelist, JOBs a worker, and reports progress in `^IRIS.Temp.MgtPortalTask` read by the Background Tasks page. In this section only Compact, Defragment, Integrity Check and the mirror database actions use it; truncate, mount, dismount, lock removal, process control, session end and deletes are synchronous. Journal profiling has its own job and temp global.
- **Auto-refresh** is a shared framework feature (timer plus persisted rate, state and sort column) used by Databases, Database Details, Processes, Process Details, Transactions, Mirror Monitor, Task Details, License Usage, Web Sessions and Background Tasks.
- **Edition and feature gating is runtime, not compile-time**: Mirror Monitor branches on `$System.Mirror.IsMember()`, Journals adds mirror choices only when mirrors exist, the LDAP caption depends on whether Kerberos is enabled, SQL Activity checks the sharding service, and Transactions degrades when the System Monitor is not running. No Cloud, ECP or Sharding item exists under System Operation.
- **Detail pages are hybrids**: Database, Process and Task details host a legacy HTML dashboard pane of value meters built in code, so a rewrite reproduces meter semantics rather than a Zen model.

**Contest areas in this section**: three of the six (task management, OS management, logs); the page mapping is the table in D4 [2].

**Leads** [11]: two truncate implementations coexist and the page looks orphaned; the Backup run form appears to create a transient `%SYS.Task`, so a replacement must choose between the backup API and a scheduled task; several legacy pages render empty on GET and are probably POST-driven. The absent mirror dialog is a row in Open questions.

**Feeds:** PRD feature catalog (System Operation tier), architecture (background-job and progress mechanism, auto-refresh, runtime gating), and the contest-minimum scope for OS management, logs and tasks.

### D3c. SMP inventory: portal shell, System Explorer, Analytics

**Bottom line.** The portal shell is one 2,823-line Zen home page plus the Zen portal application and standard-page base classes; System Explorer is a five-entry menu with 11 leaves backed by 38 portal classes, 2 more SQL pages under System Operation, about 10 legacy CSP screens and Documatic; Analytics is an 18-leaf menu (13 Business Intelligence, 5 Text Analytics) whose targets are full Zen applications, 87 classes in the DeepSee UI package alone, with Architect at 6,435 lines and Analyzer at 4,752 [16][17]. The page-by-page table is in `digests/smp-explorer-analytics-home-r1-1.md`.

**Shell features a replacement must reproduce** [16]:

- **Menu and access model.** The home finder is built from server-side nested arrays (name, title, link, disabled flag, icon, description, resource, custom resource, tags). `%CheckResources` infers each item's required resource from the URL path prefix (`/op` needs `%Admin_Operate`, `/exp` needs `%Development`, `/mgr` needs `%Admin_Manage`, `/sec` needs `%Admin_Secure`) or from the target class's RESOURCE parameter, overlays a per-page custom resource that `%Admin_Secure` holders can assign from an "Assign" mode on the home page, and disables any node whose children are all disabled. Custom resources are keyed by normalized page URL, so a portal with different routes must map its routes back to those keys or lose existing assignments.
- **Category gates.** System Operation needs `%Admin_Operate`; Explorer needs `%Development` and is disabled in `%SYS` without READ and WRITE on `%DB_IRISSYS`; Administration is disabled only when every configuration leaf is inaccessible; Interoperability needs `%Ens_Portal`; Analytics and Interoperability switch to a namespace picker when the current namespace does not support them.
- **Namespace switching** opens a dialog, then rewrites the target URL into the namespace's own CSP application; the list comes from `List^%SYS.NAMESPACE` filtered to namespaces the user can read and write. Visits to `%SYS` without a namespace parameter redirect to the user's startup namespace.
- **Header strip**: server, namespace with switch link, user with change-password link, escalation role with escalate and remove links, licensed-to, instance, and a Live, Test, Failover or Development badge; small menu Home, About, Help, Contact, Logout; a fixed 16-link "Menu" drop-down filtered by access; breadcrumb locator with an optional namespace select; per-page ribbon commands.
- **Home content**: favorites and recent items are per-user server-side lists; a "Did you know" tip; documentation and support links; a right-hand System Information panel with uptime, mirror status, four `^IRIS.Temp.SysMetrics` alerts (database space, journal space, lock table, write daemon), a System Monitor liveness check and per-namespace production status, refreshing every 10 seconds only when auto-refresh is enabled, and hidden at widths below 1,100 pixels. No license, ECP or application-error widgets live on Home; they are on the System Dashboard.
- **Search** covers menu metadata only (name, title, tags), never classes, globals, users or data, with a 220-millisecond typeahead.
- **About** exposes 14 system-overview fields and a 17-language session-language selector; **Contact** is a WRC (Worldwide Response Center) issue form; **Help** opens DocBook by a per-page help address; **Logout** calls `%session.Logout()`.
- **Portal-wide directory allow-list** restricts server file paths used by browse dialogs, relevant to every export and import feature.

**System Explorer** [16]: Classes (compile, export, import, delete, cross-links), Routines (compile, export, import, find, replace, delete, compare), Globals (export, import, find, replace, delete, view), SQL Home (a 3,909-line page with four tabs: Catalog Details, Execute Query, Browse, SQL Statements; four menus with 25 items; 17 distinct `%SQL.Manager.Catalog` queries), and Tools (WebStress, UnitTest Portal, SQL Runtime Statistics, Index Analyzer, Alternate Show Plans, Generate Report, Import Report). Globals view and edit, find and replace, SQL open table and the SQL import, export and link wizards are legacy CSP AutoPage screens, and Documatic is a plain CSP page.

**Analytics** [17]: Architect, Analyzer, User Portal, Text Analytics (Domain Architect, Domain Explorer, Indexing Results, Model Builder, Model Tester), Tools (MDX Query Tool, Term List Manager, Listing Group Manager, Quality Measures, Model Browser, PMML Model Tester) and Admin (Logs, Folder Manager, Settings, Cube Manager). Links are namespace-relative, every page inherits the `%DeepSee_Portal` or `%DeepSee_PortalEdit` resource, and a Visual Reporting sub-menu exists only inside a block comment.

**Contest areas in this section**: none, but the shell mechanics (access model, namespace switching, header, auto-refresh) frame every contest screen, and SQL and Classes are the most-used developer surfaces for the "any other screens you frequently use" invitation [2][16].

**Leads** [16]: the unread shell details are one row in Open questions.

**Feeds:** PRD portal-shell requirements (access model, namespace switching, header, favorites, search, help, about), the Explorer and Analytics tiers of the feature catalog, and the architecture decision on how menu gating is computed.

### D3d. SMP inventory: Interoperability

**Bottom line.** The Interoperability section is defined in one method, `EnsPortal.Application.GetEnsembleArray()`, with eight fixed groups (Configure, Build, View, List, Monitor, Manage, Interoperate, Test), a conditional ITK group and two dynamic hooks; 68 leaves render on this instance and 76 exist in source [13][14]. Of the 68, exactly one is Angular by default (Build > Business Rules), three more (Production, Business Processes, Data Transformations) flip to Angular only when `^%SYS("Interop","DefaultNewUI")` is set, and everything else is Zen [13]. Six Zen pages ship with an Angular twin (production configuration, BPL editor, DTL editor, rule editor, message viewer with visual trace and resend, and the read-only HL7/X12/ASTM schema viewer), and all six Angular apps call one backend, `/api/interop-editors/v7/` [15]. The export holds 224 EnsPortal classes: 62 pages and utilities, 65 dialogs, 17 composite components, and format-specific packages for EDI, HL7, DICOM, PubSub, SVG and message filters [13]. The page-by-page table is in `digests/smp-interop-r1-1.md`.

**Menu, condensed** [13]: Configure (Production, PEX Components, Business Partners, Credentials, Schedule Specs, Data Lookup Tables, System Default Settings, Purge Data Settings, Enterprise Systems, Public and External Service Registries, Message Bank Link); Build (Business Processes, Data Transformations, Generate DTL on HealthShare, Business Rules, Record Maps, CSV Record Wizard, Complex Record Maps); View (Messages, Suspended Messages, Event Log, Business Rule Log, Business Process Log, Managed Alerts, Enterprise Message Bank, Interface Maps, Interface References, Port Authority Report, plus Message Bank and enterprise views on those instance types); List (Business Processes, Data Transformations, Business Rules, Record Maps, Productions); Monitor (System Monitor, Production Monitor, Queues, Jobs, Alerts, Activity, Enterprise Monitor); Manage (Purge Management Data, Auto-Start Production, Local Archive Manager, Workflow Roles, Users, Tasks and Worklist, Publish and Subscribe, Deployment Deploy and History, Production Shutdown Groups, Setting Report configuration, Interoperability Settings); Interoperate (ASC X12, ASTM, DICOM, HL7 v2.x, UN/EDIFACT and XML, each with schema structures and a document viewer; HL7 alone has custom-schema authoring wizards); Test (Business Hosts, Data Transformations).

**Mechanics a replacement must reproduce** [13]:

- **Production lifecycle** in the production-configuration page runs entirely through `Ens.Director` (start, stop, recover, enable item, temp-stop item, delete, status, needs-update), `Ens.Job` (abort, suspend, stop) and `Ens.Queue` (abort item, abort queue); the UI exposes 18 buttons and six per-item tabs (Settings, Queue, Log, Messages, Jobs, Actions).
- **Settings widgets**: 17 composite Zen components (credentials, schedule, lookup table, SSL config, directory and file pickers, rule, DTL and BPL selectors, SQL parameter table, classpaths, external-language-server selector) sit behind every settings panel and are a parity requirement for any settings editor.
- **Access control** is per page through 30-plus distinct `%Ens_*` resources with separate view and edit resources.
- **The menu bypasses the new UI for messages**: View > Messages is hard-coded to the Zen viewer, and the Angular message viewer is reachable only from that page's "Open in the new UI" button; the Angular schema viewer only from the schema pages.
- **Eleven Zen pages embed iframes, none of them Angular**: the iframes carry message contents, legacy PubSub CSP, a DeepSee KPI chart, and compile or import output. Angular is reached only by full-page navigation, which matters for D5.
- **Hidden classes**: nine referenced classes (service registries, interface maps and references, a production-config template, three dialogs, and the PageLinks menu table) are marked Hidden and absent from the export, confirmed live [14].

**Feeds:** PRD feature catalog (Interoperability tier, the largest section by page count), architecture (Ens.Director as the lifecycle API, the interop-editors REST backend, the six Angular twins as embedding candidates), and the D5 embeddability question.

## D4. Official REST API coverage map

**Bottom line.** Two REST surfaces on the instance cover most of what the contest asks for. ## D5. Pre-built Angular editors: embeddability

**Bottom line.** Embedding InterSystems' shipped Angular editors by reference is feasible, and strongest for the three document editors. Rule, DTL and BPL editors rate high; production configuration and the message viewer rate medium; the schema viewer medium-low; the HealthShare family (credentials and OAuth security config, FHIR config, FHIR explorer, FHIR SQL) medium as opaque iframes with a separate Module Federation reuse path; Bulk FHIR and the Angular 18 mirror monitor low [24][25]. These verdicts are inferences from the cited mechanics. The per-app inventory is in `digests/irisui-embed-r1-1.md`.

**The mechanics that decide it** [24][25]:

- **InterSystems' own portal never iframes these apps; it navigates the top window** to `/ui/interop/<app>/index.html?$NAMESPACE=...&rule|DTL|BP|$PRODUCTION|SESSIONID=...`. There is no iframe pattern to copy, only a URL contract. The bundles derive their API root from a regular expression that requires `/ui/interop` in their own URL, use `<base href="index.html">` and hash routes, so they must be loaded at that exact path in place; copying them elsewhere breaks them.
- **Nothing blocks same-origin framing.** The `/ui/interop` static files are served unauthenticated with no X-Frame-Options and no Content-Security-Policy; only the classic portal page sends X-Frame-Options SAMEORIGIN.
- **The REST backend is JWT.** `POST /api/interop-editors/login` returns an ES256 access token (60-second expiry) and a refresh token (900 seconds), stored in sessionStorage and sent as a Bearer header; Basic auth also works. In a live Chrome session that already held a portal login, opening the Rule Editor logged the user in silently: a null-body login POST returned 200 and the editor rendered without a login form. Which cookie carried that login was not isolated; forcing the portal session cookie or the IRIS session token through curl returned 401.
- **A hidden embedded mode exists** in the rule, DTL and BPL editors: `VSCODE=1` hides the top bar, suppresses the automatic login, honors `READONLY=1`, posts `compatible`, `saved`, `compiled` and `badrule`, `baddtl` or `badbpl` events to the parent, and accepts inbound `auth` (username and password), `compile`, `revert`, `undo` and `redo` messages, with no origin check. The HealthShare bundles have no such contract.
- **Normal-mode chrome escapes the frame**: the logo link navigates the frame to the classic portal home, and cross-app links open sibling editors in new tabs.
- **Theming is fixed** (Tailwind and Material tokens, Noto Sans, InterSystems logo in the top bar unless hidden). **No license text** for the bundles exists in the kit; they are InterSystems-owned and should be referenced in place, never copied.

**Risk and the decision it forces** (inference) [24][25]: the silent login depends on a browser session the shipped portal establishes. If OcuPilot's own web applications join the same Group by ID group (see D4), the same silent login should carry; if not, the only alternative the bundles support is posting a username and password into the frame after `VSCODE=1`, which is a security trade-off. This is the first spike to run before the PRD commits to embedded editors.

**Feeds:** PRD (which interop editors are embedded versus rebuilt, and in which tier), architecture (iframe host component, event bridge, authentication group), and the risk register.

### D6d. Harvest: iris-couch

**Bottom line.** IRISCouch (last commit 2026-04-19) is the most mature REST-and-Angular-on-IRIS codebase among the four sibling projects, and its value to OcuPilot is pattern reuse rather than feature reuse: a disciplined `%CSP.REST` layer, an authentication ladder against IRIS users, an ObjectScript static-file server with SPA fallback, an idempotent installer, a single audit choke point and a Prometheus collector [26]. Its CouchDB semantics do not transfer. The class-by-class assessment is in `digests/harvest-iris-couch-r1-1.md`.

**Patterns worth lifting** [26]:

- **REST dispatch.** One router with a UrlMap whose routes call thin wrappers that delegate to per-subsystem handler classes and record metrics; route ordering is documented as load-bearing with a regression test for the fall-through bug it prevents. `OnPreDispatch` is the middleware seam: trailing-slash normalization, the auth ladder (cookie, then JWT, then proxy headers, then Basic, never blocking at that layer), a static-UI intercept for multi-segment deep links that UrlMap cannot match, then per-resource access enforcement.
- **Envelope discipline.** Every error goes through one `Util.Error.Render` with slug constants, internal exceptions logged in full but reported generically, and overrides of the framework's `ReportHttpStatusCode` and `Http405` so framework errors use the same envelope; handlers never construct error JSON inline.
- **Authentication.** Users are IRIS `Security.Users`, validated with `CheckPassword` in `%SYS` rather than `$System.Security.Login`; sessions are stateless HMAC-SHA256 cookies with a generated secret and constant-time comparison; JWT HS256 and proxy-header modes are opt-in. The Angular side keeps nothing client-side; the HttpOnly cookie is the session, an initializer checks it on load, a guard redirects to login, and an interceptor clears state on 401.
- **Angular hosting.** An Angular 18 standalone app with a baked base href; the built bundle is committed; a `%CSP.REST` static-file handler streams files from a configurable directory with path-traversal checks, immutable cache headers for hashed assets and no-cache for `index.html`, and falls back to `index.html` for unknown paths. The IPM manifest at HEAD is minimal (package resource only), so the documented "ZPM creates the web app" behavior is not implemented; the working install is the Installer class.
- **Installer.** Creates the web application only if absent (idempotent upgrade), creates an admin role, registers 17 audit event types guarded by existence checks, restores the namespace in the Catch block.
- **Observability.** One `Audit.Emit` entry point wrapping `$System.Security.Audit` in Try/Catch with typed helpers; structured JSON console logging; lock-free `$Increment` metrics globals rendered in Prometheus exposition format with a bounded endpoint label set.
- **Test harness.** 78 `%UnitTest` classes split into in-process handler tests and live HTTP tests through one shared request helper with header-capturing variants, an assertion that no double envelope is emitted, and pure builder methods extracted for testability.

**Reuse verdict** (inference) [26]: Reuse as-is after renaming: the error and response envelope with its framework overrides, `Audit.Emit` with the structured logger, and the HTTP test harness. Adapt: the router and `OnPreDispatch` skeleton, the static-file server (parameterize the path), the installer, the config pattern and the metrics collector. Not applicable: per-database RBAC, the users-database sync and everything CouchDB-shaped.

**Gaps to avoid inheriting** [26]: no CSRF, SameSite or Secure flag on the session cookie and no CORS handling; the mount path is baked into at least four places; the config class's "only reader" rule is violated by two direct global reads; no Docker artifacts at all.


**Feeds:** architecture spine (REST layer, auth, static hosting, installer, audit and metrics patterns) and the PRD's non-functional requirements for logging and audit.

## D7. Packaging and deployment

**Bottom line.** The lowest-risk shape for a 19-day window is one IPM module that declares a `<WebApplication>` plus `<FileCopy>` for the built Angular bundle, a second `<WebApplication>` with a `DispatchClass` for REST, `<SourcesRoot>src</SourcesRoot>` with package resources, and an `<Invoke>` for anything IPM cannot express; Docker installs at image build time through `iris.script`, and the built bundle is committed or produced in a first build stage so the same files are in the IPM archive [28][29][30]. Avoid `<CSPApplication>`, deprecated since IPM 0.9.0 even though both InterSystems templates still use it [28][29]. The element table and snippets are in `digests/packaging-r1-1.md`.

**IPM state of play** [28][32]: the current line is 0.10.x; the latest stable in Developer Community release notes is 0.10.8 and 0.10.10 is in beta as of 2026-08-26 (two sources); 0.10.x supports IRIS 2022.1 and later (single source, the README compatibility table). Since 0.9.0 IPM is no longer mapped across namespaces, so `zpm` may not exist in HSCUSTOM on a Community image; install it there or run `zpm "enable -map -globally"`. Whether the `intersystemsdc` images still ship IPM preinstalled is unverified; the current `iris-dev-template` downloads the installer itself, so install it explicitly.

**Serving an Angular app from IRIS** [29][30][31]: InterSystems' full-stack template deploys the SPA build to a CSP directory served with `ServeFiles`, alongside a separate password-authenticated REST application with a different cookie path, so the two do not share a session. The 2026 pattern in `iris-class-explorer` uses `WebApplication` and `FileCopy`, runs under a non-root base path, and answers both `/app/` and `/app/index.html`. Deep links for client-side routes need a dispatcher: a `%CSP.REST` class with a catch-all GET route that rewrites non-asset paths to `index.html` and returns `%CSP.StreamServer.Page()`, on a web application that has both a physical path and a dispatch class. Base href is set at build time to the mount path. For session sharing, one community pattern puts the static and REST applications under the same Group by ID with `UseSession` on the dispatcher; nothing was retrieved on CSRF or explicit cache headers beyond "Serve Files Always" in development to defeat gateway caching.

**Docker self-install** [29]: both InterSystems templates install during `docker build`, not at container start. A `RUN` with a bind mount starts IRIS, pipes `iris.script` into a session, and stops IRIS. The script unexpires passwords in `%SYS`, creates the namespace through a `%Installer` class, switches to it, and runs `zpm "load <dir> -v":1:1`. The 2026 dev template adds `iris merge` of a CPF file before the script. Namespace choice ("HSCUSTOM if present, else USER") belongs in `iris.script` or an installer method, not in module.xml, because the manifest is evaluated after the namespace is fixed.

**Open question that matters for this repository** [29]: this project already uses durable `%SYS` through a bind-mounted data directory, and the idea document wants installation to happen when the container comes up. No source showed the templates' build-time pattern working against a durable-`%SYS` volume, and no start-time hook (`%ZSTART`, the `-a` after-install argument, `ISC_CPF_MERGE_FILE`) was retrieved this run. The architecture must settle build-time versus start-time install before the Dockerfile is written.


**Pitfalls** [28][29][31]: deprecated `CSPApplication` and `${dbrole}` (use `${globalsDbRole}`); per-namespace IPM; gateway serving stale static files; deep links returning 404 on a serve-files-only application; the portal hiding the physical-path field once a dispatch class is set; the expired `_SYSTEM` password on Community images; the old `%ZPM.PackageManager` class name in template Dockerfiles; and the two ZPM-era videos [33], whose titles predate the rename and whose syntax the IPM wiki supersedes.

**Feeds:** architecture (packaging and install design), PRD non-functional requirements (one-step install on a clean Community image, IPM and Docker as contest bonuses), and the risk register.

## D8. Agentic co-pilot patterns in admin consoles

**Bottom line.** Across the console assistants that ship today, three patterns are table stakes: a persistent side panel with a full-screen toggle that receives current-page context by default and lets the user switch context sharing off; read-and-draft output such as generated commands and verification queries the user runs; and a propose, review, confirm flow for any write, with rationale and expected impact shown before commit [39][41][42]. Two things still differentiate: actually executing remediation from the panel under the user's permissions, which remains rare and mostly preview-gated, and audit that marks agent-initiated changes distinctly, which even Azure lacks [39][41]. InterSystems ships no assistant inside its portal; the closest precedents are community packages, and AI Hub (early access) offers role-based access to tools, Wallet credentials and approval workflows as an integration point [44]. The exemplar table is in `digests/agent-patterns-r1-1.md`.

**Exemplars, condensed** [39][40][41][42][45]: Microsoft Copilot in Azure runs agents in a sidecar panel that can act on the user's behalf, with no action performed without approval and no privilege beyond the user's, but logs actions under the user's identity with no agent marker. Amazon Q Developer in the console drafts only and refuses console changes. Gemini Cloud Assist shares page context by default, drafts snippets and verification queries, and launches multi-step investigations; Google's database agents execute validated actions such as adding an index with approval, showing rationale and expected impact, in preview with select customers. Elastic's AI Assistant reads the data on screen, runs queries under the user's permissions, and is being replaced by an agent product. IBM's Db2 console meters LLM tokens per user and tenant. Datadog, Grafana, ServiceNow, Microsoft Database Hub and JetBrains follow the same shapes with less documented detail.

**Recurring interaction patterns** [39][41][42]: side panel with full-screen toggle; page-context sharing on by default and toggleable; draft-first artifacts to copy out; propose, review, confirm with impact; "Investigate" entry points on alerts and log entries that launch a timed multi-step run with ranked hypotheses; pre-populated hand-off forms; an agent picker inside the chat; citations back to the rows used (the community `iris-session-agent` does this); suggested prompts grouped by task; inline contextual insights beside errors; record-and-generate of console actions into scripts; chat history with a retention policy. No source showed undo or rollback UI, visual diffs before apply, slash commands or streaming.

**Safety model the field converges on** [39][40][42][43]: run strictly as the user with no new privileges; read-only as the default tier; explicit approval per write; a tenant-level kill switch and per-agent enablement; explicit data-egress disclosure and opt-outs; cost controls. One practitioner framework (2026-08-31) proposes tiered autonomy for databases: observe; simulate and recommend; bounded actions with machine-checkable preconditions; human authorization for schema and access changes; and prohibited actions kept outside the agent's credentials entirely. No source documented prompt-injection defences for tool or log content.

**What users say** [43]: the loudest complaint is irrelevance and unreliability rather than danger ("unreliable and irrelevant information that required too many steps", r/AZURE, October 2025), plus hallucination and ignored instructions elsewhere. Praise centers on page context, follow-up memory and precise investigations. The practitioner caution: approve the specific proposed change with its expected impact and rollback plan, never "fix the database".

**Requirements this implies for the PRD** (inference from the cited patterns): a persistent right-hand panel with full-screen mode and per-screen suggested prompts; screen context injected by default with a visible toggle; "explain this screen" and "explain this log entry" as first-class actions; every write as a proposal with rationale, expected impact and, where possible, a rollback path, confirmed by the user; execution strictly as the logged-in user, a read-only mode, and tiered tool autonomy with prohibited operations outside the agent's reach; audit rows that mark agent-initiated changes distinctly, plus citations to the rows and API calls used; progress for multi-step runs; token usage per user; an administrator kill switch; sanitization of log content before it reaches the model, a gap the whole field shares. Support for a local OpenAI-compatible endpoint (already in the harvested provider set) turns the egress concern into a selling point for regulated IRIS shops.

**Feeds:** PRD co-pilot requirements and non-functional requirements (safety, audit, cost), brief (differentiation), and the risk register.

## Cross-dimension insights

These are the conclusions only the combination of dimensions supports, led by the one that gates the others.

1. **Authentication is the one cross-cutting decision every other dimension waits on.** Each REST application keeps its own session cookie path with SameSite Strict [22]; the vendor's Angular editors log in silently only because they share a Group by ID with the classic portal and mint a JWT [22][25]; the documentation says not to use Group by ID [20]; the embedded editors' silent login was observed but the carrying cookie was not isolated [25]; the table-editor core assumes Basic auth per call [9]; IRISCouch validates IRIS users itself and issues its own HMAC cookie [26]; the vendor templates give the SPA and the REST app different cookie paths [29]. The first architecture spike must decide between joining the `%ISCMgtPortal` group (inheriting portal login, the admin and interop-editor JWTs, and the embedded editors' silent login) and running OcuPilot's own session, and prove the choice against an embedded Rule Editor.

2. **The contest floor is already API-backed, so P0 is a thin UI over existing REST plus two custom endpoints.** The six contest areas [2] map onto about 40 pages in two portal sections [11][18], and five of the six are fully served by the hidden `/api/admin` v2 service and `/api/monitor` [21]; only "all the logs" needs custom endpoints, for messages.log and the application error log, because no REST route and no backing class exist for either [20]. That changes the shape of the 19-day plan from "build a backend" to "build screens and an agent".

3. **The hidden admin API is where InterSystems itself is heading, which makes it both the safest bet and the biggest dependency.** The dispatcher rewrites Location headers to an `/iris/api/admin/` prefix [21]; the vendor's Angular work has modernized only interoperability screens [37]; its own new-UI web apps carry the same Group by ID and JWT pattern as `/api/admin` [22][25]. The inference is that the vendor is building the administration API before the administration UI. Building on it also satisfies the contest's "powered by InterSystems IRIS management APIs" wording verbatim [2]. The counterweight is that the API is hidden and undocumented [21]; the mitigation is in D4 and Recommendation 2.

4. **The sibling MCP suite fills the custom-REST gap almost exactly.** D4's list of functions with no route anywhere [20] is, handler for handler, what the MCP suite's ObjectScript already wraps [27]. Harvest those handler bodies into OcuPilot's own `%CSP.REST` dispatcher built on the IRISCouch patterns [26] rather than inheriting the suite's `%Atelier.REST` envelope or its TypeScript-driven bootstrap.

5. **The co-pilot's core exists; its safety layer does not, and the MCP-suite sibling has it.** The session-agent core supplies providers, tool contract, registry, audit and chat history [10]; the field converges on run-as-user, propose-review-confirm, read-only default, kill switch and distinct audit attribution [39][41][43]; the session agent has none of those for writes because it blocks writes outright [10]; the MCP suite's governance (tool and action keys, default-disabled writes, a read-only preset, server-side confirm gates, a redacted audit log) is that missing layer [27]. Combining the two is the agent runtime. The differentiators the field leaves open are distinct audit marking of agent-initiated changes, execute-with-approval from the panel, and a local OpenAI-compatible model that keeps data on the instance [10][39][41].

6. **Streaming is the largest engineering gap, and users punish exactly the symptom it causes.** The harvested loop is one blocking call per turn with a 90-second provider timeout and a 300-second gateway timeout [10]; the loudest complaint about console assistants is that they are slow, irrelevant and take too many steps [43]. P0 needs at least progress delivery for multi-step turns; server-sent events can follow.

7. **The legacy CSP pages are the inventory's blind spot, and they cluster inside the contest areas.** Backup, SQL Gateway, Web Gateway Management, task-manager email, enable and disable auditing and the Security Advisor [18], plus the task-builder wizard with about 60 fields, the application error log, the messages log, system usage and the dashboard [11], have no exported source. Task creation and two of the log viewers are contest-area screens. Pull those `.csp` files from the container before writing the P0 forms.

8. **Embed versus rebuild splits cleanly along the URL contract, and interoperability can wait.** Of the 68 interoperability leaves, 67 are Zen [13]; the three document editors embed with a hidden embedded mode and events, production configuration and the message viewer embed as opaque pages, and the rest must be rebuilt or linked [24]. None of it is in the contest's six areas [2], so interoperability is post-contest work where embedding buys the three hardest editors for little cost once authentication is solved.

9. **The four install patterns in evidence contradict each other, and this repository already uses durable `%SYS`.** The vendor templates install at image build time [29]; the MCP suite bootstraps at runtime over the Atelier API [27]; IRISCouch commits its bundle and relies on an installer class [26]; the idea behind this project wants install on container start with a bind-mounted data directory. The reconciliation is one IPM module as the single source of truth (web applications, file copy, an installer invoke) that the Dockerfile loads at build time and an idempotent installer re-checks at start, but the build-time and durable-volume interaction is unverified.

10. **The rules reward listing early and improving continuously.** The Open Exchange listing must exist before applying, earlier submissions are listed higher on the contest page, improvements are allowed through the voting week, and the field is empty [2][6][8][34]. The strategy that follows is a submittable build listed on 2026-09-14, then two weeks of visible improvement, rather than a single drop on 2026-09-27.
