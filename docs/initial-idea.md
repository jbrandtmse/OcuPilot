I want to create a Agentic System Management Portal for InterSystems IRIS.   The goal is to take first place in the "InterSystems Programming Contest: Build Your Own Management Portal" (https://openexchange.intersystems.com/contest/48 , https://community.intersystems.com/post/intersystems-programming-contest-build-your-own-management-portal)

The basic concept is to incrementally build a comprehensive system management portal that features a co-pilot like agent on the right hand side.  Always visible and the main conduit for editing within the portal.  We should base this on preliminary work done in my ../iris-session-agent project.   The agent should be context aware of what is on the screen at all times.   Edits to settings should be allowed through tools that the agent has access to.

Incremental build is important because there is a limited timeframe we're dealing with for the contest.   Features and functionality of the portal must be prioritized with the minimum requirements mentioned in the contest rules as the top prioritiy.   We'll then add additional tools and screens harvesting from previous work done in my ../iris-session-agent, ../iris-execute-mcp-v2, and ../iris-table-editor projects and the orginal System Management Portal http://localhost:52774/csp/sys/UtilHome.csp?$NAMESPACE=%SYS

The portal will be built in Angular and served from IRIS.   It will be packaged as this workspace with a docker instance.   It can also be deploy with ZPM/IPM (https://www.youtube.com/watch?v=NVEOe-F5O80, https://www.youtube.com/watch?v=havPyPbUj1I and search for the official IPM documentation).
Where possible, we should use the official APIs exposed in IRIS through the %Api classes (./irissys/%Api*) and documented in ./irisdocs/.   If nessesary, we will also add our own custom Api like I have previously done for ../iris-execute-mcp-v2.   Like ../iris-execute-mcp-v2 any custom API should attempt to self install or be deployed with IPM.  (and in the case of the docker project in this workspace, should self install when the container is upped.).  We should not assume that any of my previous projects are installed (although they may be present, and we should avoid package collisions).   Any custom objectscript will install in HSCUSTOM namespace if present or User namespace if not present.

The portal must have an agent configured to run properly.  If an agent isn't configured, once the user is logged in an agent configuration screen (similar to what is avaliable in ./iris-session-agent) will be presented to the user.  All of the agent model options in ../iris-session-agent should be supported and the framework should be extendable like ../iris-session-agent.

The plan is to start with a minimal set of features (with agentic "co-pilot" support) as dictated in the context rules and get as many of them done before the end of the contest but eventually completely build out to where the portal has functional parity with the existing System Management Portal + all the functions in ../iris-session-agent + ui equivalents of the functions supported in ../iris-execute-mcp-v2.

Where possible, we should use the pre-built editors and by embedding them.  A copy of these are in ./irisui/

./irisdocs/, ./irislib/, ./irissys/, ./irisui/ and all the IRIS related projects in ../ can be used as reference.  You should in particular review ./irisdocs/, ./irissys/%Api*, ./irislib/%Atelier, ../iris-execute-mcp-v2 and ../iris-session-agent.   You should also review the existing System Management Portal ObjectScript code in ./irislib/EnsPortal.
